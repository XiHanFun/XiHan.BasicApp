# 插件方案

> 状态：设计草案（2026-11-23），未拍板。第 11 节是需要拍板的事项。

## 0. 一页结论

- **插件是什么**：第三方交付、运行期安装、与宿主隔离的扩展。它贡献操作、权限码、页面与扩展点，不随 BasicApp 重新编译，崩溃只影响自己。
- **不重造宿主**：直接用框架的插件宿主（进程外 `Plugins.OutOfProcess` 为主，`Plugins.Wasm` 可选）。框架已经解决了清单、握手、代理操作经完整管道、回调身份与租户约束、崩溃重启与健康降级；BasicApp 只补应用层：安装与授权管理、权限码作用侧、页面与菜单、套餐门控、前端呈现、接进现有能力的扩展点。
- **新包**：Tier 3 可选模块 `XiHan.BasicApp.Extensions`（包名 `extensions`）。不叫 `Plugins`：框架已经占用了 `PLUGINS_*` 错误码与 `plugins.*` 消息键。
- **谁装、谁用**：平台安装、平台授权；租户经套餐开通、经角色授权使用。插件拿不到主库连接。
- **前端**：缺省是声明式页面（宿主按插件给的页面描述渲染，没有插件脚本）；受信任且签名的插件才能带脚本页面。
- **前置条件**：框架要先补一项——运行期加载的插件操作也发布 HTTP 路由与接口文档（第 9 节 F1）。有了它，安装、启停、升级都不用重启宿主。

## 1. 概念与边界

| | 能力包 | 可选模块 | 插件 |
| --- | --- | --- | --- |
| 谁写 | 本仓库 | 本仓库 | 第三方或独立团队 |
| 何时进来 | 编译期 | 编译期，`BasicApp:Modules:<名>:Enabled` 开关 | 运行期安装、启用 |
| 载体 | 同进程程序集 | 同进程程序集 | 子进程（任意语言）或 Wasm 沙箱 |
| 能访问 | 一切 | 一切 | 只有握手声明的操作、订阅，以及授予了的回调 |
| 数据 | 主库 | 主库 | 自己的存储；主库数据只能经回调调宿主操作 |

不做：

- 进程内插件。框架的进程内宿主给插件独立容器、不向应用登记操作与权限码，接不进 BasicApp 的业务面。
- 运行期编译源码（在管理界面录入代码、宿主进程里编译后挂成接口）。这等于开放任意代码执行：代码以宿主权限运行，能直接读写主库、取到任何服务；编出的程序集对整个进程生效，租户边界随之失效；程序集加载进默认上下文后卸不掉，反复更新会累积；只在处理请求的实例上生效，多实例不同步；也带不来菜单、权限码与配置。要「写一段代码就上线」的场景，用 Wasm 插件。
- 租户自装插件。插件进程是全平台共享的，租户只决定用不用。
- 插件市场（远程仓库、在线检索）。先把本地上传安装做完整。

## 2. 现状与差距

| # | 现状 | 差距 | 去处 |
| --- | --- | --- | --- |
| 1 | `MapXiHanOperations()` 在映射时对 `OperationRegistry` 取快照 | 运行期 `LoadAsync` 的代理操作没有 HTTP 路由，只对 `IOperationInvoker` 可见；卸载后路由还在、返回 `KERNEL_NOTFOUND_001` | 框架 F1 |
| 2 | 框架清单 `xihan.manifest.json` 的 Schema 是 `additionalProperties: false` | 页面、权限码作用侧这些应用信息写不进框架清单 | 旁挂清单 `basicapp.plugin.json`（4.3） |
| 3 | 插件宿主只把权限码登记进框架 `PermissionRegistry` | `PermissionCatalog` 里没有的码 `AllowsSide` 两侧都放行，角色、套餐、权限目录页面都看不到 | 运行期权限来源（5.5） |
| 4 | 页面目录与权限目录是启动期登记的 DI 单例，菜单从它们对齐 | 插件页面进不了菜单 | 运行期页面来源（5.5） |
| 5 | 前端 `resolveView` 只认 `src/modules/*/views/**/index.vue` 的 glob | 插件页面没有加载路径 | 插件视图加载器（6.1） |
| 6 | 框架的插件目录与授予来自 `XiHan:Plugins:*` 配置 | 管理界面里批准的授予要从库给出 | 运行期 `LoadAsync` 由调用方给授予，框架已支持（5.4） |
| 7 | 回调以插件主体执行，Access 对不是本应用用户的主体不做授予收窄 | 没有给插件主体授权的地方；数据范围按用户 ID 解析 | 插件授权（5.6） |
| 8 | 到现在各包都没有登记领域事件 | 插件没有业务事件可订阅 | 首批事件主题（5.7） |
| 9 | 接口文档的分组在 `BasicAppOpenApi.Options()` 里静态列出，按清单 ID 归属成组 | 运行期加载的插件进不了分组，也没有单独的分组文档 | 框架 F1 + 运行期分组来源（5.3） |

## 3. 总体结构

```text
平台管理员 ─上传 .xhplugin─▶ Files（对象存储）
          ─检查 / 安装 / 授权 / 启停 / 升级 / 卸载─▶ Extensions 操作
                                   ├─ 写平台库：sys_plugin / sys_plugin_version / sys_plugin_grant
                                   └─ 提交后广播 basicapp.extensions.changed

每个实例的 PluginReconciler（托管服务，启动时与收到广播时各对齐一次）
  读库 → 把包同步到本地缓存 App_Data/plugins/<清单 ID>/<版本>/ → 核对散列与签名
  → IPluginHost.LoadAsync(目录, 批准的授予) / UnloadAsync
  → 运行期目录：权限码（作用侧、审计）→ PermissionCatalog；页面 → 菜单；扩展点 → Contracts 登记的代理

插件进程 ⇄ 本机 gRPC xihan.plugin.v1 ⇄ 代理操作 → 宿主完整管道（租户、授权、套餐门控、审计、事务）

前端：菜单下发组件路径 plugins/<短名>/<页>/index
  → 声明式页面：宿主渲染 SchemaPage + XEditModal
  → 脚本页面：import /plugins/<清单 ID>/<版本>/web/<页>.js（共享宿主运行时）
```

## 4. 插件包与清单

### 4.1 包格式

`.xhplugin` 是 zip：

```text
xihan.manifest.json          框架清单（RFC-0002），原样交给框架宿主
basicapp.plugin.json         旁挂清单：应用层信息
runtimes/<rid>/…             进程外插件按运行时标识分目录（linux-x64、linux-arm64、win-x64…）
module.wasm                  Wasm 插件（与平台无关）
pages/<页>.json              声明式页面描述（可选）
web/…                        脚本页面的构建产物（可选）
locales/<区域>.json × 10     前端文案：页面标题、声明式页面的字段与按钮
SIGNATURE                    发布者签名（可选，生产环境要求）
```

解包时只取当前平台的 `runtimes/<rid>/`，展开成框架要的「一个目录一个插件、清单在根」；当前平台没有对应运行时即拒绝安装。

### 4.2 框架清单的约束

框架清单不改，BasicApp 安装时另加约束：`kind = plugin`；`isolation` 在 `BasicApp:Extensions:Isolations` 允许的范围内（缺省只有 `out-of-process`）；不写 `contributes.pipeline`（Wasm 中间件先不开放，见 5.7）。

### 4.3 旁挂清单 `basicapp.plugin.json`

```json
{
  "pluginApi": "1",
  "name": "crm",
  "publisher": "contoso",
  "runtimes": [ "linux-x64", "win-x64" ],
  "permissions": [
    { "code": "crm.crm-customers.read", "scope": "tenant" },
    { "code": "crm.crm-customers.create", "scope": "tenant", "audited": true },
    { "code": "crm.crm-customers.delete", "scope": "tenant", "audited": true }
  ],
  "pages": [
    {
      "code": "crm.customers",
      "route": "/plugins/crm/customers",
      "titleKey": "crm.pages.customers",
      "icon": "lucide:contact",
      "permission": "crm.crm-customers.read",
      "view": { "kind": "schema", "file": "pages/customers.json" }
    }
  ],
  "callbacks": [ "identity.users.read" ],
  "extends": [
    { "point": "workbench.widget", "code": "crm.pipeline", "operation": "crm-widgets.pipeline" }
  ]
}
```

安装时逐条静态核对（插件代码一行都不跑）：

| 项 | 规则 |
| --- | --- |
| `name`（短名） | `^[a-z][a-z0-9-]{1,31}$`；全平台唯一；不得是保留名（全部内置包名、`extensions`、`plugins`、`custom`、`system`、`api`…） |
| 操作 ID | 框架清单 `contributes.operations` 的每个资源段等于短名或以 `<短名>-` 开头（`crm-customers.list` → `POST /api/crm-customers:list`），不会撞上内置资源 |
| 权限码 | 集合与框架清单 `contributes.permissions` 完全一致；`<短名>.<资源>.<动作>`，资源段是本插件某个操作的资源段；`scope` 取 `platform` / `tenant` / `both` |
| 页面 | 页面码 `<短名>.<页>`，路由以 `/plugins/<短名>/` 开头，`permission` 是本插件的码或宿主已登记的码 |
| `callbacks` | 插件主体要调的宿主权限码，都要已登记；写了就要求框架清单 `permissions` 含 `capability:kernel.pipeline` |
| `extends` | `point` 在 5.7 的表里，`operation` 在本插件的操作里 |
| 文案 | `locales/` 齐 10 个区域；消息键首段是短名；错误码 `<短名大写>_<KIND>_<NNN>` |
| 接口文档 | 握手的消息目录要有分组显示名与说明 `openapi.groups.<短名>.name` / `.description`，以及每个资源的 `openapi.tags.<资源>.name`，与内置包同一规则；这几项只能在握手后核对，缺了即这次加载失败 |
| 冲突预检 | 操作 ID、推导出的 HTTP 路由、权限码与当前登记表比对 |

## 5. 后端：Extensions 包

### 5.1 定位与装配

- Tier 3 可选模块，开关 `BasicApp:Modules:Extensions:Enabled`，与其他可选模块同一语义。依赖 Contracts、Runtime 与 Files（包文件存对象存储）；对 Access、Tenancy 只经 Contracts 的接口。
- 模块开着时宿主装 `OutOfProcessPluginsFeature`，`Isolations` 含 `wasm` 时再装 `WasmPluginsFeature`。框架的 `XiHan:Plugins:*:Directories` 与 `Grants` 一律不写：插件全部由 BasicApp 在运行期按库加载，启动期没有插件，也就不会因插件登记冲突让宿主起不来。
- 没装任何插件时不起任何进程。

### 5.2 实体（平台库，不实现 `IMultiTenant`）

| 表 | 内容 | 索引 |
| --- | --- | --- |
| `sys_plugin` | 安装记录：清单 ID、短名、当前版本、是否启用、是否允许脚本页面、最近一次加载的错误码 | `ux_sys_plugin_manifest_id`、`ux_sys_plugin_name`（软删除，`[EntityIndex]`） |
| `sys_plugin_version` | 每个上传过的版本：文件 ID、SHA-256、大小、发布者与签名结论、框架清单与旁挂清单原文 | `ux_sys_plugin_version_plugin_id_version` |
| `sys_plugin_grant` | 批准的授予：种类（`capability` / `fs.read` / `fs.write` / `net.outbound` / `config` / `binding` / `callback` / `ui`）、值、批准人与时间 | `ux_sys_plugin_grant_plugin_id_kind_value` |

运行态（`Ready` / `Degraded` / `Failed`、进程 ID、重启次数）是每个实例自己的，不落库，读 `IPluginHost.Plugins` 与健康项 `plugins.<清单 ID>`。

### 5.3 操作、权限码与页面

| 操作 ID | HTTP | 权限码 | 说明 |
| --- | --- | --- | --- |
| `plugins.list` | `POST /api/plugins:list` | `extensions.plugins.read` | 分页列表 |
| `plugins.get` | `GET /api/plugins/{id}` | `extensions.plugins.read` | 详情：清单、贡献、授予、版本 |
| `plugins.status` | `GET /api/plugins/{id}:status` | `extensions.plugins.read` | 本实例运行态与健康 |
| `plugins.inspect` | `GET /api/plugins:inspect?fileId=` | `extensions.plugins.install` | 只读：解包核对，返回贡献清单、申请的授予、冲突与风险提示，不落库 |
| `plugins.install` | `POST /api/plugins` | `extensions.plugins.install` | 从已上传文件安装，连同批准的授予；装好是停用状态 |
| `plugins.upgrade` | `POST /api/plugins/{id}:upgrade` | `extensions.plugins.install` | 换版本；贡献的增删在 `inspect` 里先列出 |
| `plugins.rollback` | `POST /api/plugins/{id}:rollback` | `extensions.plugins.install` | 退回上一个版本 |
| `plugins.grant` | `POST /api/plugins/{id}:grant` | `extensions.plugins.grant` | 改批准的授予（整体替换） |
| `plugins.enable` / `plugins.disable` | `POST /api/plugins:enable` 等，`{ ids }` | `extensions.plugins.update` | 批量启停 |
| `plugins.delete` | `DELETE /api/plugins?ids=` | `extensions.plugins.delete` | 卸载 |
| `plugin-views.list` | `GET /api/plugin-views` | 只要求认证 | 当前用户可见的插件页面描述与这些页面要调的操作路由，前端运行期用 |

- 包文件走现有的 Files 上传端点，不新增普通端点。
- 管理用的权限码都是 `Platform` 侧、写操作 `audited`。
- 错误码 `EXTENSIONS_VALIDATION_*`（包格式、命名、旁挂清单与框架清单不一致）、`EXTENSIONS_CONFLICT_*`（短名或清单 ID 已安装、与已登记的操作 / 路由 / 权限码冲突）、`EXTENSIONS_DENIED_*`（未签名或发布者不受信任、脚本页面未获准）、`EXTENSIONS_UNAVAILABLE_*`（当前平台没有对应运行时）；消息键补齐 10 个区域。
- 页面 `extensions.plugins`，路由 `/extensions/plugins`，挂在「系统服务」目录。
- 接口文档按插件分组：每个加载成功的插件一组，组名是短名、归属是清单 ID，排在内置包之后（序号从 1000 起），显示名与说明取插件消息目录。全量 `/openapi.json` 的 `x-tagGroups` 里多出这一组，`/openapi/<短名>.json` 只含这个插件的操作；卸载即撤回。分组来源由 Extensions 提供，宿主的静态分组不变。

### 5.4 运行期对齐（PluginReconciler）

- 托管服务，在结构升级与种子之后启动：对每个启用的插件确保本地缓存（缺了从对象存储取、核对散列），以批准的授予 `LoadAsync`；成功后把权限码、页面、扩展点接进运行期目录；失败只让这个插件 `Failed`，错误码记进 `sys_plugin`，应用进入 `Degraded`。对齐有总时限，完成前就绪检查不通过。
- 管理操作在事务里改库，提交后本实例立即对齐，同时以广播方式发 `basicapp.extensions.changed`，其他实例收到后各自对齐（单实例用内存代理，配了 RabbitMQ 跨实例）。
- 停用：先 `UnloadAsync`（框架按归属撤回代理操作与权限码，在途调用照常完成或以 `PLUGINS_UNAVAILABLE_001` 结束），再撤回运行期目录与扩展点代理。
- 升级：同一清单 ID 不能同时加载两份，所以先卸旧版再载新版；新版失败即重载旧版，错误码留给管理员。
- 卸载：停用之后清掉菜单节点、角色与用户授予、套餐白名单、委托与约束规则里引用插件权限码的行（确认框先列出要删的内容），删除本地缓存；插件自己的数据宿主不碰。

### 5.5 权限码、套餐与菜单

- Contracts 加运行期来源接口（权限描述、页面描述各一个，带变更令牌），Access 的 `PermissionCatalog` 与页面汇总把它们和启动期登记的片段合并。插件权限码由此带上作用侧与审计标记：作用侧拦截、角色授权页、套餐编辑页、权限目录都能看到。
- 套餐门控不用改：租户侧的插件码缺省不在任何套餐里，平台把它们加进套餐，租户才用得上。
- 菜单：插件页面按「页面菜单归登记」对齐，缺省挂在新目录「插件应用」（`MenuDirectories` 加 `custom.plugin-apps`）；停用只隐藏节点、保留运营的展示调整，卸载才删。
- 插件变更后让授权快照、有效权限与菜单缓存失效。

### 5.6 插件主体与回调

- 回调以插件主体执行（主体 ID 是清单 ID、认证方案 `Plugin`），经完整管道。平台在授权页批准两类东西：
  - 框架授予：清单 `permissions` 里的 `capability:*`、`fs.*`、`net.outbound:*`，以及 `config:<配置节>`、`binding:<绑定名>`，作为 `LoadAsync` 的授予；
  - 回调权限码：旁挂清单 `callbacks` 列的宿主权限码，写进框架授予存储、主体为插件。
- 租户侧回调只能带当前这次调用的租户（框架强制），还要过套餐门控（租户上下文里 `EditionPermissionFilter` 自动生效）。
- 数据范围按用户解析，插件主体不是用户：缺省为「无」（受数据范围约束的查询查不到行），要「全部」由平台在授权页显式勾选。
- 主库绑定 `db` 永不授予。要持久化的插件用运维另配的专用绑定（自己的库或 schema），租户隔离由插件按上下文里的 `xihan.tenant` 自己负责；以后再考虑宿主提供按租户隔离的插件存储操作集。

### 5.7 扩展点：插件接进现有能力

| `point` | 接到 | 插件操作的形状 |
| --- | --- | --- |
| `workbench.widget` | `IWorkbenchWidgetProvider` 的代理 | 只读，返回小组件数据（与内置小组件同一 DTO） |
| `workflow.business` | `IWorkflowBusinessHandler` 的代理 | 审批通过 / 驳回等回调 |
| `printing.data-source` | 打印数据源注册表（要改为可在运行期增减） | 只读，按字段契约返回数据 |
| `notification.channel` | 通知渠道发送器（后续） | 发送一条消息 |

- 事件：插件在握手里订阅 `basicapp.<包>.<事件>`。前提是 BasicApp 先按 D7 的规则登记第一批公开事件（用户创建 / 停用、租户开通、部门变更、流程结束），主题集中在 `Contracts/Topics.cs`，并像 `realtime.json` 一样导出一份事件契约给插件开发者。
- `Expose` 含 `Mcp` / `Ai` 的插件操作随 F1 进 MCP 与 AI 工具目录。
- Wasm 管道中间件能改写任何请求，前几期不开放。

## 6. 前端

### 6.1 路由与视图

- 菜单里的组件路径 `plugins/<短名>/<页>/index`，菜单项另带插件元数据（清单 ID、版本、视图种类）。`resolveView` 认出首段 `plugins` 时交给插件视图加载器，其余不变；找不到同样抛错，不静默回退。
- 模块门禁与 `viewKeys()` 只管 `src/modules`，插件路径不进门禁。

### 6.2 声明式页面（缺省）

- `pages/<页>.json` 描述列、筛选、工具栏与行操作（行内用「更多」菜单）、编辑表单字段（每个字段有可见标签，说明进 `XFieldLabel` 的 `help`），按钮绑定插件的操作 ID 与权限码。
- 宿主的 `PluginSchemaView` 用 `SchemaPage` + `XEditModal` + `XhFormRoot` 渲染，字段类型限定在 `SchemaPage` 已支持的范围；操作路由取 `plugin-views.list`，校验约束取操作的 JSON Schema，错误按 `code` 分支。
- 没有插件脚本，任何插件都可以用；视觉、主题、键盘与无障碍和内置页面一致。

### 6.3 脚本页面（受信任插件）

- 要求：授予里有 `ui:script`，且包已签名、发布者受信任。
- 插件用 `@xihan-basicapp/plugin-kit`（Vite 预设）构建，把 `vue`、`vue-router`、`pinia`、`vue-i18n`、`@xihan-ui/vue` 与 `@xihan-basicapp/plugin-runtime` 设为外部依赖。宿主构建时多出一个 `plugin-runtime` 入口，从同一张模块图里再导出这些模块（保证 Vue 与组件库是同一个实例），并在 `index.html` 写入 import map。
- `plugin-runtime` 是带大版本的公开面：`invoke(operationId, request)`、权限门控、按短名取文案、`SchemaPage` / `XEditModal`、当前租户与主题令牌。`pluginApi` 大版本不匹配时页面显示错误态，不加载脚本。
- 插件静态资源由宿主在 `/plugins/<清单 ID>/<版本>/web/` 提供，按版本长期缓存。同源脚本拥有当前用户的全部前端权限，所以只给受信任插件。

### 6.4 文案

插件 `locales/<区域>.json` 按语言懒加载，挂在短名命名空间下，与 `registerModuleLocales` 同一套回退链。后端消息键随握手的消息目录进宿主本地化器。

### 6.5 管理页

`src/modules/extensions/views/plugins/index.vue`（`SchemaPage`）+ 安装向导（上传 → 检查报告：贡献、申请的授予、冲突与风险 → 批准授予 → 安装）+ 详情抽屉（概览、贡献、授予、运行状态、版本与回退）。

### 6.6 契约

`contracts export` 不加载插件，`frontend/contracts/openapi.json` 永远只有内置操作，CI 漂移门禁保持确定。插件开发者用 `plugin-kit gen` 从运行中宿主的分组文档 `/openapi/<短名>.json` 生成自己的客户端：一个插件一份，只含它自己的操作，不混进内置契约。

## 7. 安全模型

| 环节 | 规则 |
| --- | --- |
| 谁能装 | 只有平台侧持 `extensions.plugins.install` 的主体 |
| 包可信 | SHA-256 必核；签名按 `BasicApp:Extensions:TrustedPublishers` 校验；`AllowUnsigned` 只在 Development 缺省打开；脚本页面一律要求签名 |
| 隔离选择 | 不可信代码用 Wasm；进程外插件的能力等同运行它的系统账户，生产用最小权限账户或容器运行宿主 |
| 授予 | 清单申请的每一项都要平台逐项批准，缺一项即不加载；主库绑定永不授予 |
| 调用 | 插件操作与回调都经完整管道：租户、授权、作用侧、套餐门控、审计 |
| 前端 | 声明式页面没有插件脚本；脚本页面只给受信任插件 |
| 审计 | 管理操作全部审计；插件操作按旁挂清单的 `audited` |

## 8. 配置

```json
{
  "BasicApp": {
    "Modules": { "Extensions": { "Enabled": true } },
    "Extensions": {
      "CacheDirectory": "App_Data/plugins",
      "Isolations": [ "out-of-process" ],
      "AllowUnsigned": false,
      "TrustedPublishers": [],
      "MaxPackageSizeMegabytes": 200,
      "ReconcileTimeoutSeconds": 60
    }
  }
}
```

框架节 `XiHan:Plugins:OutOfProcess` 的时限与重启策略照框架缺省，需要时再写；`Directories` 与 `Grants` 不写。键同步 `ConfigurationSchema.json` 与文档。

## 9. 框架回灌

| # | 事项 | 理由 |
| --- | --- | --- |
| F1 | HTTP 操作端点改用随 `OperationRegistry` 变更的端点数据源：运行期登记的代理操作发布路由，卸载即撤回；OpenAPI 文档随之刷新，分组除了 `OpenApiOptions.Groups` 的静态列表，还可以由应用提供带变更令牌的分组来源；MCP 发 `tools/list_changed`。gRPC 不在范围 | 没有它，安装与启停只能重启生效，卸载后的路由还会留着，插件也进不了接口文档分组 |
| F2 | 插件宿主的状态变化可订阅（事件或变更令牌） | 管理页实时显示运行态，不轮询 |

不走 F1 的退路是「启停重启生效」：启动期把库里的插件写成框架配置交给发现阶段。它会让插件登记冲突变成宿主启动失败，不建议作为终态。

## 10. 分期

| 期 | 内容 | 退出条件 |
| --- | --- | --- |
| E0 | 框架 F1（F2 可同期），发包后升锁 | 框架测试覆盖运行期加载与卸载的路由与文档 |
| E1 | Extensions 后端：实体、全部管理操作、对齐服务、运行期权限与页面来源、菜单、缓存失效、健康；示例插件（不引用 XiHan 包的 .NET 进程外插件，内存 CRUD） | 集成测试：安装 → 启用 → HTTP 调用 → 租户隔离 → 套餐门控 → 分组文档出现插件 → 停用后路由与分组都撤回 → 卸载清理 |
| E2 | 前端：管理页、安装向导、详情抽屉、声明式页面渲染 | `pnpm check` / `test` / `build` 通过；端到端：装示例插件、菜单出现、走一遍增删改查 |
| E3 | 签名与可信发布者、升级与回退、多实例广播 | 两实例集成测试 |
| E4 | 脚本页面：`plugin-runtime`、import map、`plugin-kit` | 示例插件带一个脚本页面，在生产构建下跑通 |
| E5 | 扩展点（工作台小组件、工作流业务处理、打印数据源）、首批领域事件与事件契约 | 示例插件各接一个 |

之后再考虑：Wasm 管道中间件、宿主提供的插件存储、插件市场。

## 11. 待拍板

1. **包名**：`Extensions`（建议）——避开框架的 `PLUGINS_*` 错误码与 `plugins.*` 消息键。
2. **F1 先行**：先在框架补运行期路由再做 BasicApp（建议），还是先用「重启生效」上线？
3. **允许的隔离级别**：缺省只开进程外（建议），Wasm 由配置打开？
4. **脚本页面**：要不要做 E4，还是只做声明式页面？
5. **插件主体的数据范围**：缺省「无」、由平台显式给「全部」（建议）？

## 12. 风险

- 进程外插件没有操作系统级沙箱，「批准授予」只是声明层面的约束，`fs.*` 与 `net.outbound:*` 加载时核对、运行时不拦。要强隔离只能用 Wasm 或在容器层收紧。
- 多实例下各实例的插件状态可能短暂不一致（广播到达前）：调用打到还没对齐的实例时得到 `KERNEL_NOTFOUND_001` 或旧版本的结果。
- 插件操作的 `Expose` 来自插件自己的声明，超出 `Http` 的操作不受 `OperationExposureTests` 守护，安装检查要按同一规则拒绝「超出 HTTP 却不是只读」的操作。
- 卸载会删掉授予与菜单，再装同一插件要重新授权。
