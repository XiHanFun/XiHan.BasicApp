# 为什么是 6.0

本页说明 6.0 为什么选择在 XiHan.Framework 5 上重写而不是迁移 5.x 代码，以及重写带来的主要设计取舍，适用于评估是否采用 6.0 的技术负责人与开发者。完整的决策记录见仓库 `nextdocs/下一代总体方案.md` 第 1、4、10 节。

## 背景

XiHan.Framework 5 采用了一套新的应用写法：能力包（`IFeature` + 清单）、操作契约（一个方法对应一个操作）、管道阶段中间件、RFC 9457 错误与按操作 ID 推导的路由。5.x 的 BasicApp 建立在框架 4.x 的 Dynamic API、Castle 拦截与约定扫描之上，与 5.0 的写法不兼容。

6.0 因此选择重写：功能与 5.x 对齐，结构与框架 5 保持一致，不保留兼容层。

## 不采用迁移的原因

框架侧曾用迁移工具把 5.x 代码转换到 5.0，结论如下：

1. 迁移产物仍是旧结构。每个 Dynamic API 方法被包装成委托式操作类，权限码保留冒号形式并转调旧的权限检查器，当前用户依赖兼容包装。框架随后撤销了这套迁移规则集。
2. 权限码文法、路由与响应信封、`tenant_id` / `row_version` 的列类型、平台数据的可见性，这四个问题都源于 4.x 的结构。重写时可以直接按新规则设计。
3. 框架 5 不再包装 SignalR、模板引擎、升级编排、机器人渠道、签名与加密中间件、国内第三方扫码登录。迁移需要逐项承接，重写时这些能力直接成为 BasicApp 的能力包。
4. 5.x 自身有若干待清理的问题：工作台查询为空实现、约束规则只实现了 SSD、会话角色激活没有写入口、组件路径命名不统一、壳层手写 URL、大量裸 px 白名单。迁移会原样保留它们。

## 全局决定

| 编号 | 决定 | 理由 |
| --- | --- | --- |
| D1 | 能力包 + 操作契约；HTTP 路由由操作 ID 推导，错误使用 RFC 9457，成功响应不加信封 | 这是框架 5 的标准写法，一份契约同时用于 HTTP、gRPC、OpenAPI、MCP 与 AI 工具 |
| D2 | 5.x 的 Saas 模块拆分为能力包与宿主，按 Tier 0–3 单向依赖 | 每个包包含自己的实体、操作、权限、页面、种子、文案与测试，层级由架构测试检查 |
| D3 | 主键使用 UUID v7；租户 ID 使用字符串；平台数据不实现 `IMultiTenant`；时间统一为 UTC `DateTimeOffset` | 框架 5 的仓储对 `IMultiTenant` 严格相等过滤，`TenantId = 0` 表示平台的做法不再成立；UUID 消除前端的数字字符串换算 |
| D4 | 权限码 `<包>.<资源>.<动作>`，操作 ID `<资源>.<动词>`，按钮直接使用操作的权限码 | 权限目录从操作登记派生，不再分别维护权限码与按钮码 |
| D5 | 前端 API 层由 `/openapi.json` 生成，错误按 `code` 分支 | 前后端契约不一致由生成器与 CI 检出 |
| D12 | 不提供 5.x → 6.0 的数据迁移 | 主键、列类型、权限码与表名全部改变，6.0 从空库初始化 |

## 设计原则

装配显式。6.0 不使用约定扫描、`IScopedDependency` 或拦截器，服务在 `IFeature.Configure` 中登记，横切逻辑以管道阶段中间件实现。一个包提供了什么，以它的 Feature 类为准。

单一事实源。权限目录来自操作登记，菜单来自页面登记，前端类型来自 OpenAPI，枚举文案来自后端消息目录，同一信息不在两处维护。

失败以值表示。可恢复的失败返回 `Result` / `Error`，错误码 `<包>_<KIND>_<NNN>` 决定 HTTP 状态与 gRPC 状态；异常只用于编程错误与基础设施故障。

缺省收紧。每个操作必须显式声明 `Expose`（编译期诊断 `XHG004`），管理操作只发布到 HTTP，选定的只读操作才发布到 MCP 与 AI 工具；权限码缺省要求认证。

文案与代码分离。每个包有一个消息常量类和 10 种区域的 JSON 文案，错误只携带键与参数，由宿主按 `Accept-Language` 翻译。

## 限制

| 项 | 说明 |
| --- | --- |
| 数据迁移 | 不提供 5.x → 6.0 的迁移工具。切换到 6.0 的部署需要在 6.0 上重新录入租户与账号；5.x 部署继续由 `release/v5` / `hotfix/v5` 维护 |
| 协议兼容 | 不提供 5.x HTTP API 的兼容层，对接方按[接口对接指南](./api-guide)调整 |
| Native AOT | 不是目标。SqlSugar、MailKit、Scriban 等依赖不支持 AOT；操作登记仍按框架要求使用源生成的 `JsonSerializerContext` |
| 完成度 | N3（工作流、打印、代码生成、聊天）与 N4（AI）尚未实现，评估时以[功能清单](./features)中已落地的部分为准 |
