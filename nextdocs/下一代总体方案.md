## 0. 一页结论

**做什么**：在 `backend-next/` 与 `frontend-next/` 从零实现一个功能与 v5.9.1 对齐、架构按 XiHan.Framework 5 原生范式设计的 BasicApp，版本线定为 **6.0**。它同时是 Framework 5 的官方参考实现与新用户起点模板（框架 `01-框架定位.md` 第七节对 BasicApp 的定位）。

**不做什么**：不做 4.x API 的运行期兼容、不保留 `ApiResponse` 信封与 `/Controller/Action` 路由的双轨、不走 `xihan migrate v4` 的机械迁移（该路线产出的 BasicApp `next` 分支已被你删除，只剩框架文档里的经验）、不做 5.x → 6.0 的数据迁移（完全重做，D12）。

**五个决定性选择**（详见第 4 节）：

| # | 选择 | 一句话理由 |
| --- | --- | --- |
| D1 | 能力包（`IFeature` + 清单）+ 操作契约（一方法一操作）；HTTP 按 5.0 推导路由，错误用 RFC 9457，成功无信封 | 这是 5.0 的唯一一等公民写法；一份契约同时得到 HTTP / gRPC / OpenAPI / MCP / AI 工具 |
| D2 | Saas 巨石（149k 行、72 实体）拆成 **19 个能力包 + Host**（Tier 0 基座 2、Tier 1 身份租户 4、Tier 2 平台能力 7、Tier 3 可选 6，见 5.2）；包间依赖分层、单向 | 对齐框架「能力包」模型；每包自带实体、操作、权限、菜单、种子、文案、测试 |
| D3 | 主键 UUID v7；租户 ID 字符串；平台数据不实现 `IMultiTenant`；并发戳 32 位字符串；时间 UTC `DateTimeOffset` | 5.0 的 SqlSugar 仓储对 `IMultiTenant` 严格相等过滤、无租户看不到任何行，4.x「TenantId = 0 表示平台」在 5.0 不成立；UUID 消掉前端 `NumericString` 换算层 |
| D4 | 权限码 `<包>.<资源>.<动作>` 点分三段；操作 ID `<资源>.<动词>`；**按钮即操作**，不再有第二套按钮码 | 内核 `PermissionDefinition` 只接受点分小写；权限目录从操作注册表派生，303 个权限码 + 226 个按钮码两处维护变一处 |
| D5 | 前端 API 层由后端 `/openapi.json` 生成；错误按 `code` 分支；Tailwind 直接映射 `--xh-*` 令牌，不再双轨 | 契约漂移靠生成器和门禁拦截，78 组手写 facade 与 `*.types.ts` 不再手工同步；设计令牌桥（`xihan-ui.css` 三遍映射）是 4.x 最厚的一层历史债 |

**规模**（盘点数字，用来看量级）：后端 91 个实体、154 个 Dynamic API 服务（折合约 520 个方法）、303 个权限码、32 个种子、74 个页面与 226 个按钮；前端 `src` 约 10.5 万行、`packages` 约 9.7 万行、78 组 API facade、168 个测试文件。重写不是省工作量，而是用同样量级的工作换一个没有兼容层、与框架同形的结构。

## 1. 为什么重写而不是迁移

框架侧已经把「机械迁移」这条路跑过一遍（`05-开发计划.md` P5-02 / P5-04 / P5-12，2026-10-24 至 26），结论可以直接拿来用：

1. **迁移产物不是 5.0 的样子。** `xihan migrate v4` 把每个 `[DynamicApi]` 方法生成一个「委托式操作类」，主构造函数注入原服务再转调；权限码仍是冒号形式，按名注册 `permission:<code>` 策略转调 4.x 的 `SaasPermissionChecker`；`ICurrentUser` 用生成的兼容包装；工作单元靠 `ICurrentUnitOfWorkAccessor`。能跑，但每一层都是垫片。框架随后在 ADR-0021（2026-10-26）撤掉了这套 4.x 规则集，只留通用迁移机制。
2. **四件事在迁移路线上是「待拍板」，在重写路线上是「设计起点」**：权限码文法、路由与响应信封、`tenant_id` / `row_version` 列类型迁移、平台行可见性语义。它们都是从 4.x 结构倒推出来的难题，从零设计时根本不存在。
3. **5.0 删掉的不只是写法，还有能力边界。** SignalR、网关、模板引擎、升级编排、Bot 渠道、签名 / 加密中间件、国内 OAuth 扫码，框架明确不再包装（`06-BasicApp迁移清查.md` 第 2.2 节）。迁移要逐处「承接」，重写时它们就是 BasicApp 自己的包。
4. **4.x BasicApp 内部也有一批要清的债**（后端与前端盘点的「现状痛点」）：`WorkbenchQueryService` 空壳、约束规则只实现 SSD、Schema 隔离未实装、会话角色激活无写入口、Component 命名 PascalCase 与 kebab 混用、`defineResource` 零使用、`shell` 层 70 个手写 URL、1476 处裸 px 白名单、空的 `diagram` 包。迁移会把它们原样带过去。

重写的代价是功能对齐的工作量，第 7 节的对齐矩阵和第 8 节的分期门槛就是为此准备的。

## 2. 目标与边界

### 2.1 目标

- **功能对齐**：`docs/features.md` 列出的全部能力在 6.0 有去处（第 7 节矩阵），少数明确删减项已在第 10 节拍板。
- **架构同形**：应用只用 5.0 的一等公民概念（能力包、操作、管道阶段、Provider、消息键），不自建平行机制。
- **一份契约多端复用**：同一操作既是 HTTP 端点，也可按需成为 MCP tool / AI 工具；前端客户端从同一份 OpenAPI 生成。
- **可被框架验证**：BasicApp 自己实现的 Provider（租户存储、权限授予存储、审计落库、工作流存储）引用对应 `*.Conformance` 套件自证。
- **结构有门禁**：实体落点、权限码登记、操作命名、消息键齐全、前端权限码与契约漂移，都由测试守护，不靠文档约定。

### 2.2 非目标

- 不提供 4.x HTTP API 的兼容层或双协议并行。
- Native AOT 不是目标（SqlSugar、Redis、Jwt、RabbitMQ、S3 都是非 AOT 包），但操作登记按框架要求使用源生成的 `JsonSerializerContext`。
- 不在 6.0 引入 EF Core、Naive UI 或第二套脚手架（沿用现行 AGENTS.md 禁令）。
- 不为旧库做「原地升级」，也不提供 5.x → 6.0 的数据迁移工具；6.0 从种子全新初始化（D12）。

## 3. 设计原则

1. **装配显式。** 没有约定扫描、没有 `IScopedDependency`、没有 Castle 拦截；服务在 `IFeature.Configure` 里登记，横切逻辑是管道阶段中间件。
2. **契约先行。** 操作、权限、页面、消息键是包的公开面，先定后写；破坏性变更只在大版本。
3. **一个事实源。** 权限目录来自操作注册表，菜单来自页面登记，前端类型来自 OpenAPI，枚举文案来自后端消息目录；不允许两处维护同一件事。
4. **边界刚、内部柔。** 包之间只经 `Contracts` 的接口与消息主题往来；包内部怎么分 Domain / Infrastructure 目录由包自己决定，但目录名全仓统一。
5. **批量优先。** 对已有对象按标识的写操作（删除、状态、授权、撤销）只提供集合入参的操作，单条是集合的特例（框架 ADR-0012 的同一规则）。
6. **文案不进代码。** 每包一个 `<包>Messages` 常量类 + `Localization/<区域>.json` × 10 种区域；错误只带键与参数，由宿主在 Egress 翻译。
7. **失败是值。** 可恢复失败返回 `Result` / `Error`，不抛业务异常；异常只用于编程错误与基础设施故障。
8. **默认收紧。** 每个操作显式写 `Expose`（框架生成器诊断 `XHG004` 在编译期强制，修订（十七））：管理操作只 `Http`，选中的只读操作追加 `Mcp | Ai`，供内部服务调用的追加 `Grpc`；权限码缺省要求认证。

## 4. 全局决定

### D1 应用形态与协议

- 每个业务能力是一个 `IFeature`（需要启停逻辑时 `IHostedFeature`），手写 `Manifest`：`Id = "xihan.basicapp.<包>"`，`Kind = Capability`，`Requires` 用能力 ID（`persistence.relational@1`、`security.authorization@1`、`multitenancy.context@1`、`messaging.queue@1`、`caching.distributed@1`、`scheduling.jobs@1`…），包间依赖写成 `basicapp.<包>@1`（见 D2）。
- 每个公开方法是一个 `[Operation("<资源>.<动词>")] : IOperation<TRequest, TResponse>`，`HandleAsync` 返回 `ValueTask<Result<TResponse>>`。
- HTTP 路由由操作 ID 推导（`spec/conventions/operation-ids.md`、ADR-0015），统一前缀 `XiHan:Protocols:Http:RoutePrefix = "/api"`：
  - `users.create` → `POST /api/users`（201）；`users.get` → `GET /api/users/{id}`；`users.update` → `PUT /api/users/{id}`；`users.delete` 以集合入参 → `POST /api/users:delete`；
  - 带分页对象的 `users.list` → `POST /api/users:list`；集合级动词 `users.export` → `POST /api/users:export`；实例级动词 `users.lock` → `POST /api/users/{id}:lock`；
  - 单例资源 `profile.get` → `GET /api/profile`。
  - 声明 `ReadOnly = true` 的查询动词（ADR-0041）在请求没有嵌套对象时走 GET、字段走查询串：`departments.tree` → `GET /api/departments:tree`，`roles.members` → `GET /api/roles/{id}:members`，`roles.by-user` → `GET /api/roles:by-user?userId=…`（修订（十七））；有嵌套对象的仍 POST。
- 成功响应正文就是响应 DTO；失败是 `application/problem+json`（`type = urn:xihan:error:<code>`、`code`、`traceId`、本地化的 `detail`；VALIDATION 错误另带字段级 `errors`（字段键 → 按调用方区域翻译的消息数组），其余错误按白名单带标量 `details`，ADR-0024 补充）。客户端只依赖 `code` 与 `errors`。
- gRPC 是内部服务调用面（第 10 节第 9 项）：宿主映射 `MapXiHanGrpc()` 与 `MapXiHanProto()`，只发布显式带 `Expose.Grpc` 的操作（5.4）；方法名由操作 ID 推导（`users.get` → `/xihan.basicapp.Users/Get`，`XiHan:Protocols:Grpc:Package = "xihan.basicapp"`），protobuf 消息由同一份操作 Schema 推出，`.proto` 从 `GET /operations.proto` 取；元数据复用 HTTP 头映射（`authorization`、`accept-language`、`traceparent`、`xihan-deadline` / `grpc-timeout`），内部服务拿同一 JWT 调用，经完整内核管道（租户、权限、事务）；错误映射按 `spec/protocol/grpc.md`（VALIDATION → `InvalidArgument`、DENIED → `PermissionDenied`，尾部元数据 `xihan-error-code`）。Kestrel 为 gRPC 单独开 HTTP/2 端点，只监听内网地址；前端不用 gRPC。
- 不能用操作表达的端点（浏览器重定向、文件上传下载、SignalR、OIDC 发现文档、静态资源）用普通 ASP.NET Core 端点，挂 `RequireXiHanPermission(...)` / `RequireXiHanAuthentication()`，静态资源与 Hub 用 `BypassXiHanPipeline()`。
- 需要进接口文档的普通端点（上传、下载与预览、导出结果、代码生成产物、验证码图片）必须带 `WithName` / `WithSummary` / `Accepts` / `Produces` 元数据，由框架 OpenAPI 生成器收进同一份 `openapi.json`；它们的 JSON 请求 / 响应只能引用某个操作的根 Schema：`WithXiHanOperationSchema("files.get")` 显式声明，或按类型自动匹配（上传成功返回的就是 `files.get` 的响应）；引用不到即 `PROTOCOLS_VALIDATION_010`，不另做推导（ADR-0032）。OIDC 端点由发现文档自述，SignalR 不是请求响应，健康检查与重定向不带 `Accepts` / `Produces`，都不进文档。

### D2 包切分与依赖层级

把 4.x 的 Saas + Core + Web.Core 拆成四层（后端细节见 5.2）：

```text
Tier 0 基座       Contracts → Runtime
Tier 1 身份租户    Identity → Tenancy → Organization → Access      （严格按箭头单向）
Tier 2 平台能力    Settings | Notification | Files | Auditing | Maintenance | OpenPlatform | Realtime
                  （只依赖 Tier 0/1，彼此不引用，经 Contracts 接口与消息主题协作）
Tier 3 可选模块    Workbench | Workflow | Printing | CodeGeneration | Chat | AI
Host              XiHan.BasicApp.Host
```

规则：只能向下依赖；同层之间不引用；跨层协作用 `Contracts` 里的接口（例如 `IWorkbenchWidgetProvider`、`IExportProvider`、`IPrintDataSource`、`IWorkflowBusinessHandler`）与消息主题（CloudEvents 信封）。由 `XiHan.BasicApp.Architecture.Tests` 守护。

**已拍板（2026-10-27）**：按能力包拆分，5.2 清单共 19 包 + Host。备选「Saas 仍是一个项目、内部按目录分」不采用：149k 行一个程序集、一个 `JsonSerializerContext`、一份清单，和框架「能力包」模型对不上。

### D3 标识、租户与协议字段

| 项 | 6.0 | 4.x | 理由 |
| --- | --- | --- | --- |
| 主键 | `Guid`（UUID v7，框架 `GuidV7IdGenerator`） | 雪花 `long` | 时间有序、JSON 即字符串、前端无精度问题；工作流引擎已是 UUID v7。框架已补完整的雪花 `long` 生成器供其他应用（`SnowflakeIdFeature`，9.3），BasicApp 不用 |
| 租户 ID | `string`，文法 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`，即 4.x 的 `TenantCode` | `long`，0 = 平台 | 框架 `IMultiTenant.TenantId` 是字符串，JWT `tenant` 声明直接解析 |
| 平台数据 | **不实现 `IMultiTenant`**；需要「属主」的读共享实体用显式列 `OwnerTenantId`（平台值为常量 `platform`） | `TenantId = 0` | 5.0 仓储对 `IMultiTenant` 严格过滤，无租户看不到任何行；平台管理员没有租户上下文 |
| 并发戳 | `string ConcurrencyStamp`（32 位） | `long RowVersion` | 框架协议 |
| 时间 | `DateTimeOffset`，库内 UTC，响应 ISO 8601 带 `Z` | 服务端按 `X-Timezone` 换算 | 换算移到客户端（6.8）；删掉 `X-Timezone` 头 |
| 审计字段 | 框架维护 `CreatedAt / ModifiedAt / DeletedAt / IsDeleted / ConcurrencyStamp / TenantId`；应用在 `Contracts` 定义 `IHasCreator / IHasModifier / IHasDeleter`（`string? CreatedBy` 等，值为主体 ID）并由 `Runtime` 填充 | AOP 注入 | 框架没有操作人字段 |
| 枚举 | JSON 字符串枚举（源生成上下文 `UseStringEnumConverter`） | 同 | 前端得到字面量联合类型 |

**已拍板（2026-10-27）**：主键 UUID v7；平台数据不实现 `IMultiTenant`（第 10 节第 1、4 项）。你同时要求框架提供完整的雪花 `long` 生成器（`IIdGenerator<long>`，含机器位分配与时钟回拨处理，与 `GuidV7IdGenerator` 同样装配），已作为框架能力落地（`b1ca15f1`，ADR-0033：`SnowflakeIdFeature` 显式装配、`IWorkerIdSource` 机器位来自配置或 `IDistributedLock` 租约、回拨超阈值 `PERSISTENCE_UNAVAILABLE_004`、无机器位 `PERSISTENCE_UNAVAILABLE_005`，GuidV7 缺省不变）；BasicApp 6.0 不使用它，前端没有 `NumericString`。

### D4 权限码、操作 ID 与页面

- 权限码：`<包>.<资源>.<动作>`，例 `identity.users.read`、`access.roles.grant`、`tenancy.tenants.transfer-owner`。由各包在 `Configure` 里 `context.AddPermission(...)` 登记；应用层再用 `PermissionDescriptor`（包、资源、动作、作用侧 Platform / Tenant / Both、是否审计）包装一层，权限目录种子从注册表派生，不再手写 `SaasPermissionDefinitions`。
- 操作 ID：资源段与权限码的资源段同词；资源名全应用唯一，只在歧义时加前缀（`chat-conversations`、`print-templates`、`workflow-definitions`、`ai-providers`）。
- 页面登记：每包一个 `Pages.cs`（页面码、路由、组件路径、图标、排序、所需权限码、子页面）。组件路径 = 路由路径去前导斜杠 + `/index`，一律 kebab-case；前端不再做多候选匹配。
- **按钮即操作**：页面上一个写动作对应一个操作，前端门控直接用该操作的权限码。4.x 的 226 个按钮码取消。

### D5 前端契约

- `frontend-next/scripts/gen-contracts.mjs` 从运行中后端或导出文件（`dotnet run -- contracts export`，见 5.13）读取一份 `openapi.json`（每个操作带 `x-xihan-permission` / `x-xihan-policy`，`components.x-xihan-permissions` 是权限定义表，ADR-0031；上传、下载等普通端点也在这一份里，见 D1），生成 `packages/contracts/{types.ts, operations.ts, permissions.ts, enums.ts}`；生成物入库，CI 用「重新生成后 diff 为空」做漂移门禁。
- 运行时客户端只做：拼路由、放头（`Authorization`、`Accept-Language`、`traceparent`）、解包 Problem Details 为 `ApiError { code, status, detail, traceId, errors?, details? }`、按 `code` 触发刷新令牌与锁屏、把 `errors` 交给表单按字段显示。

### D6 数据层

- `Persistence.SqlSugar` **方式一**（`SqlSugarPersistenceFeature` 按回调创建作用域客户端）。ADR-0022 之后作用域客户端带 `default` 与 `shard` 两个连接：带分片的租户调用多一个 `shard` 连接，实体按 `IEntityConnectionSelector` 落点，缺省规则是「`[Tenant(configId)]` 显式指定 → 实现 `IMultiTenant` 的实体落 `shard` → 其余落默认连接」，工作单元经 `AsTenant()` 在全部连接上开启、提交、回滚。这恰好就是 D3 的「库决定协议」：平台库实体不实现 `IMultiTenant`，永远在默认连接；租户库实体实现它，随租户分库。`Runtime` 不再自建连接路由，只负责回调里的 `DbType`、连接串、`AopEvents` 与表名列名约定（snake_case 继续用 SqlSugar 特性或 `EntityService` 回调）。
- 跨库事务是顺序提交，不是两阶段提交（ADR-0022 写明）：需要严格原子性的写入放同一个库；租户开通这类平台库 + 租户库的写路径接受「第二个连接提交失败时第一个已提交」，由操作做补偿。
- 操作人字段、差异日志经回调里的 `ConnectionConfig.AopEvents`（`DataExecuting` / `DataExecuted`）挂，当前主体由 `Runtime` 的 Transaction 阶段中间件放进作用域供回调读取（N0 冒烟确认回调能拿到作用域服务）。
- 简单读写走框架 `IRepository<TEntity, TKey>`（含批量）；带 `[SplitTable]` 的按月分表日志也走仓储（ADR-0023：仓储自动走分表入口，`EntityQuery<T>.Within(时间范围)` 限定扫描的表）；分页、投影、联表走包内 `Queries/` 里的查询类直接用 `ISqlSugarClient`，**必须**经 `Runtime` 的 `TenantScopedQuery` 助手加租户与软删除条件（框架没有全局过滤器），连接用 `SqlSugarUnitOfWork.ConnectionFor(typeof(T))` 取。写库前 `SqlSugarUnitOfWork.EnsureTransactionAsync`。
- 表结构由应用管理：`Host/Schema/<版本>/*.sql`（PostgreSQL 方言，可重复执行）+ 版本台账；`InitTables` 只开在 Development。`InitTables` 只建缺表、加缺列（ADR-0040）：PostgreSQL 上非可空的数值 / 枚举 / 布尔 / Guid 新列按 CLR 缺省值回填旧行；给已有行的表新增非可空字符串或日期时间列不受支持，实体里声明成可空，或重建开发库。

### D7 领域事件与消息

框架派发（ADR-0025，2026-10-27）：仓储写入成功后工作单元登记带事件的聚合，Transaction 阶段提交前经 `IDomainEventDispatcher` 把事件打成 CloudEvents 信封按主题批量发布（装配了 `OutboxFeature` 时与业务写入同事务，精确一次；没有发件箱时先于提交、至多一次）。6.0 的规则：聚合在方法里记录事件；每种事件在所属包的 `Configure` 里 `AddDomainEvent<TEvent>(topic, type, jsonTypeInfo, subject?)` 显式登记（未登记即 `MESSAGING_VALIDATION_003`，带事件却没有派发器即 `PERSISTENCE_VALIDATION_003`，都是装配错误，第一次调用就暴露）；操作里不再手动发布。处理器 `IMessageHandler` 按主题订阅，经完整管道执行（自带租户与事务）。主题常量集中在 `Contracts/Topics.cs`，格式 `basicapp.<包>.<事件>`；宿主必装 `OutboxFeature`。

### D8 校验

框架提供（ADR-0024，2026-10-27）：内核 `ValidationMiddleware` 在 Validate 阶段按操作的请求 JSON Schema 校验载荷，再对实现 `IValidatableObject` 的请求执行自校验；`[Required]`、`[Range]`、`[StringLength]`、`[MinLength]`、`[MaxLength]`、`[Length]`、`[RegularExpression]` 由 `Kernel.Generators` 折进 Schema（同时进入 OpenAPI，前端生成的类型与校验约束同源）；HTTP 载荷在进管道前绑定，不合法的请求不进 Idempotency / Transaction / Handle。6.0 的规则：请求 record 用 DataAnnotations 表达单字段约束，跨字段规则实现 `IValidatableObject`（文案用 `key.L()` 取调用方语言）；业务规则校验一律在领域服务，返回 `Result`。应用不写校验中间件，也不要基类。

### D9 本地化

后端：10 种内置区域（`en-US` 默认、`zh-CN`、`zh-TW`、`ja-JP`、`ko-KR`、`de-DE`、`es-ES`、`fr-FR`、`pt-BR`、`ru-RU`），每包 `Localization/<区域>.json`；`Localization.Database` Provider 让运营在后台覆盖译文（替代 4.x 没有的「多语言管理」）。前端同 10 种区域，按语言懒加载。**已拍板（2026-10-27）**：只用内置 10 种，`hi-IN` 不保留，4.x 的 `hi-IN` 资源不带过来。

### D10 认证与授权的分工

- 框架只校验令牌（`Security.Jwt`，HS256）与判定策略；**签发、刷新、会话、2FA、第三方登录、模仿**都是 `Identity` 包的操作与中间件。
- 授予存储用框架 `Security.Database`（ADR-0027：`IPermissionGrantStore` 在新作用域只读工作单元读仓储、有界 TTL 缓存；`PermissionGrantRecordStore` 批量授予 / 撤销逐项结果）；`Access` 包不再自己提供 `security.authorization@1`，只在框架授权之上注册自己的 `IPolicy` 承担角色继承、Deny、委托、套餐门控、ABAC 条件，角色与用户的授权行同时写入框架的 `PermissionGrantRecord`；数据范围与字段安全是应用自己的中间件与查询条件。

### 5.4 操作契约约定

- **命名**：标准动词 `create / get / list / update / delete`；写动作用动词原形（`lock`、`reset-password`、`transfer-owner`、`publish`、`export`）；查询变体用 `list-<限定>`（`users.list-online`）或独立资源（`online-sessions.list`）；`get` / `list` 以外的只读动词一律声明 `ReadOnly = true`（ADR-0041：MCP 只读提示、HTTP 走 GET）。
- **分页**：`Contracts` 定义 `PageRequest { Page { Index, Size }, Filters[], Keyword, Sorts[] }` 与 `PageResult<T> { Items, Total, Page }`；`Size` 上限 500。`list` 带 `PageRequest` 的操作自动落到 `POST /<资源>:list`。
- **批量**：删除、状态、授权、撤销一律集合入参，请求体是对象 `{ "ids": [...] }`（HTTP 适配器只合并 JSON 对象，不接受顶层数组）；响应 `BatchResult { Succeeded[], Failed[{ id, code }] }`。
- **文件**：只有 JSON 能进操作；上传、下载、预览、导出文件下载是普通端点 `POST /api/files/upload`、`GET /api/files/{id}/content`，挂 `RequireXiHanPermission`，元数据管理是操作。
- **暴露**：每个操作显式写 `Expose`，`Architecture.Tests` 对没写的判失败（框架 `OperationAttribute.Expose` 缺省 `All` 且特性 `sealed`，应用改不了缺省；程序集级缺省列入 9.4 待提）。管理类写操作只 `Expose.Http`；只读的目录类操作（字典、枚举、菜单、我的待办、统计）加 `Expose.Mcp | Expose.Ai`，供 AI 助手作为工具调用（消息目录提供 `<操作 ID>.description`）；供内部服务调用的操作加 `Expose.Grpc`（清单随 N1 操作表定，不另开第二套内部 API）。 修订（十六）定稿：超出 `Http` 的操作逐个登记在 `Architecture.Tests` 的 `OperationExposureTests`，没登记的必须恰好是 `Http`；只读指动词是 `get` / `list` 或声明了 `ReadOnly = true`（修订（十七））；N2 起新写的字典、枚举、我的待办、统计类只读操作在同一张表里登记。
- **授权**：`Permission = IdentityPermissions.UsersRead` 或 `Policy = "authenticated"`（自助操作）；匿名操作（登录、验证码、找回密码、刷新令牌）不写两者，并在 `Architecture.Tests` 的匿名白名单里登记。
- **返回**：找不到 → `Error.NotFound(IdentityErrors.UserNotFound, IdentityMessages.UserNotFound, MessageArguments.Of(("id", id)))`；冲突 → `Conflict`；越权 → `Denied`。锁屏（4.x 的 423）用 `IDENTITY_DENIED_002`，HTTP 状态 403，前端按 `code` 进锁屏。

### 5.5 实体协议与应用基类

框架只有接口，应用允许保留基类（框架迁移规范允许「应用基类保留，只换它实现的框架接口」）。`Contracts/Entities/`：

| 基类 | 组合 | 用途 |
| --- | --- | --- |
| `AppEntity` | `IEntity<Guid>`、`IHasConcurrencyStamp` | 关联表、无审计 |
| `AppRecord` | `AppEntity` + `IHasCreationTime` + `IHasCreator` | 日志、流水、投递记录（只增） |
| `AppAuditedEntity` | `AppRecord` + `IHasModificationTime` + `IHasModifier` + `ISoftDeletable` + `IHasDeleter` | 默认选择 |
| `AppAggregateRoot` | `AppAuditedEntity` + `IAggregateRoot<Guid>`（`DomainEventBuffer`） | 有行为的聚合 |
| `TenantXxx` 变体 | 上述 + `IMultiTenant` | **只用于租户库实体**（见下） |

**库决定协议**（取代 4.x 的「平台库 = 目录库」口诀，语义相同）：

- 平台库实体（目录：租户、套餐、用户与账号安全、会话、OAuth、角色与全部授权、权限目录、菜单、参数、字典、模板、存储配置、编号规则、任务定义、AI 配置）**不实现 `IMultiTenant`**。需要区分「平台的还是某租户的」用显式列 `OwnerTenantId`（平台 = `TenantIds.Platform`，即常量 `platform`），由 `Contracts` 的 `IOwnedByTenant` 协议与 `Runtime` 的规约 `OwnedByCurrentTenantOrPlatform()` 读共享、`OwnedByCurrentTenant()` 写不共享。用户、会话等账号域实体用 `HomeTenantId`（注册地）列，登录等无租户阶段的操作显式按它查。
- 租户库实体（部门、岗位、用户部门、文件、导出、通知投递、聊天、工作流、用户统计、8 类日志、版本台账）**实现 `IMultiTenant`**，由框架仓储严格过滤，并随租户分库物理隔离。
- 平台跨租户扫租户库（到期处理、日志清理、书签轮询）走 `Runtime` 的 `ITenantScopeRunner.RunPerTenantAsync`：为每个目标租户发起一次带租户的独立调用（`IOperationInvoker.InvokeAsync` 或 `App.CreateContext`），不在同一上下文里切换租户。
- 软删除实体的唯一索引末列包含 `is_deleted`（沿用 4.x 规则，由结构测试守护）。

### 5.8 身份与安全（Identity）

- **登录**：`auth.login`（密码）、`auth.login-by-email-code`、`auth.login-by-phone-code`、`auth.send-code`、`auth.captcha`、`auth.register`、`auth.request-password-reset`、`auth.reset-password`、`auth.refresh`、`auth.logout`、`auth.switch-tenant`、`auth.lock` / `auth.unlock`、`auth.me`、`auth.permissions`，均 `Expose.Http`。两段式 2FA（TOTP / 邮件 / 短信）沿用票据模式。
- **令牌**：`Identity` 签发 HS256 JWT（`sub` = 用户 ID、`tenant` = 当前租户、`sid` = 会话、`act` = 模仿者），`Security.Jwt` 校验；刷新令牌不透明，存 `SysUserSession`。密码 PBKDF2、密码历史、强制改密参数沿用。
- **第三方登录**：GitHub、Gitee、Google、QQ、微信、企业微信、飞书、钉钉（扫码 / 账号）以普通端点 `/api/oauth/{provider}/challenge`、`/callback` 实现（浏览器重定向），回调后换成本系统令牌。
- **会话与在线**：`SysUserSession` 存 JTI；`sessions.list / revoke`（批量）；在线状态 = 活跃会话 + `Realtime` 的连接标记。
- **个人中心**：`profile.*` 单例资源（资料、改密、2FA、联系方式、设备、登录日志、三方绑定、API 凭证、通知偏好、注销）。
- **模仿登录**：`impersonation.candidates / start / stop`，策略参数与守卫沿用；横幅信息进 `auth.me`（修订（十二）已落地：范围不填即发起人当前上下文，租户主体钉在自己的租户）。

### 5.9 授权模型（Access）

- **RBAC**：角色、角色继承（只存直接边，图上推导）、用户 / 角色授权各带 Grant / Deny、委托并入快照；合并优先级沿用「用户 Deny > 用户 Grant > 角色 Deny（本链）> 角色 Grant」。Grant 行同步写入框架 `Security.Database` 的 `PermissionGrantRecord`（框架 `PermissionChecker` 负责基础判定），Deny、继承、委托、套餐门控由 Access 登记的 `IPermissionFilter`（框架 ADR-0039：授予命中之后逐个收窄）在其上收窄（修订（十三）：原写「`IPolicy`」，按名的策略拦不到 `permission:<码>`）；快照存 `ISharedCache`，授权变更事件触发失效。
- **作用侧**：权限带 Platform / Tenant / Both；平台主体与租户主体分别只能命中各自作用侧。
- **套餐门控**：有效权限与 `Tenancy` 的套餐白名单求交（`Tenancy` 经 `Contracts.IEditionGate` 暴露，`Access` 消费）。修订（十三）已落地：作用于 `auth.permissions`、`permissions.list` 与判定（`EditionPermissionFilter`）；租户未绑定套餐即不受限（与 4.x 不同）。
- **ABAC**：权限条件（组内 AND、组间 OR）、访问策略（平台 / 租户两层、三段时机、六个模板、命中记录）、试算与盘点操作。
- **数据范围**：`SelfOnly / DepartmentOnly / DepartmentAndChildren / All / Custom`，`Runtime.TenantScopedQuery` 提供 `ApplyDataScope(ownerColumn, departmentColumn)`，6.0 把它扩到用户、部门成员、文件、导出、通知等列表（4.x 只作用于用户列表）。
- **字段安全**：按实体 × 字段 × 目标，6 种脱敏策略，响应过滤 + 查询门控 + 写校验。
- **约束规则**：SSD 评估沿用；DSD、互斥、基数、条件的评估补齐（第 10 节第 7 项），四种类型走同一评估器，违规处理方式沿用 4.x 的配置项。
- **菜单与页面**：汇总各包 `Pages.cs` 为菜单种子；`menus.*` 管理操作；`auth.permissions` 返回权限码、菜单树与页面码。修订（十四）已落地：页面节点的来源字段归登记、展示可定制并可恢复，运营另建目录与外链，没有按钮节点。

### 5.10 多租户（Tenancy + Runtime）

- 租户目录用框架 `MultiTenancy.Database`（ADR-0026：`TenantRecord` 经仓储读写、单例目录有界 TTL 缓存、`TenantRecordStore` 批量增改删并失效目录与分片缓存）。`SysTenant` 仍是 Tenancy 的业务实体（套餐、到期、配额、成员、状态），开通、启停、改连接串时在同一工作单元里同步写 `TenantRecord`（ID、显示名、是否启用、`ConnectionString` 等属性）；租户状态、到期、配额由操作维护。
- 解析链：JWT `tenant` 声明 → Baggage `xihan.tenant`（框架默认顺序）；不再支持查询串与 `X-Tenant-Id` 头（减少自报租户的面）。平台主体无租户声明。
- 隔离模式：Field（默认）与 Database；Schema 隔离在 4.x 未实装，6.0 **不再保留**该枚举值。
- 开通三步沿用：`tenants.create` →（Database 时）`tenants.initialize-database` → `tenants.initialize-admin`；所有权转移、支持成员、成员邀请、我的订阅沿用。
- 分库连接：`Runtime` 的 `TenantConnectionRegistry` 按租户维护 `SqlSugarScope` 的 `ConfigId`，连接串用数据保护加密存储。

### 5.11 消息、通知、实时

- 站内通知、定向投递（All / Role / Department / User）、强制阅读、横幅 / 弹窗、阅读统计沿用；渠道扇出（邮件、短信落发件箱，机器人直发）用 `IMessageHandler` 订阅 `basicapp.notification.published`。
- 发件箱：业务消息用框架 `OutboxFeature`；邮件 / 短信的「待发送记录」仍是应用表（可重发、可查）。
- 模板：Scriban 直接引用（框架不再包装），租户模板优先、平台兜底。
- Bot 渠道（钉钉、飞书、企业微信、Telegram、邮件、短信）作为 `Notification` 包的 `Infrastructure/Channels/*`，接口 `IMessageChannel`；Telegram Webhook 是普通端点。
- 实时：`Realtime` 包直接用 ASP.NET Core SignalR（`/hubs/notification`、`/hubs/chat`），Hub 端点 `BypassXiHanPipeline()`，用 ASP.NET Core `AddAuthentication().AddJwtBearer`（与 `Security.Jwt` 共用密钥）认证；推送契约 `IRealtimePush.ToUserAsync(userId, method, payload)`；推送载荷与操作响应共用 DTO（UUID 已是字符串，不再手工投影）。

### 5.12 调度、工作流、文件、日志、配置

- **调度**：业务作业用 `AddJob<T>`（代码登记）与 `IJobScheduler.ScheduleAsync`（运行时登记，替代 4.x `DynamicJobWorker`）；多实例用 `Scheduling.Database`（五张框架表）；`Maintenance` 提供作业与运行历史的管理操作与 Cron 校验，不再有自己的 `SysTask` 调度表。内建作业：用户统计聚合、日志保留清理、聊天保留清理、租户到期处理、访问策略命中落库、导出任务执行。
- **工作流**：按 P5-12 的方式作为 `workflow.execution@1` 显式 Provider，SqlSugar 三存储 + `ICacheStore` 租约锁 + 逐库书签轮询；定义 JSON 直接是 5.0 `WorkflowJson`；审批业务契约 `IWorkflowBusinessHandler` 在 `Contracts`，`Access` 的授权申请是参照实现。前端流程设计器需适配 5.0 定义形状（6.9）。
- **文件**：`IBlobStore` 之上保留 `SysFile` / `SysFileStorage`（多副本、主副本、秒传、预签名、校验）；存储配置动态创建 `IBlobStore` 实例（本地用 `ObjectStorage.FileSystem`，S3 / OSS / COS / MinIO 用 `ObjectStorage.S3` 的 `ServiceUrl`）。
- **日志与审计**：8 类日志保留按月分表（SqlSugar 分表特性，仓储按 ADR-0023 自动分表）；框架操作审计经 `Auditing.Database` 落库（ADR-0028：有界队列后台批量写入、按写入序号分页），`Auditing` 包只做查询面与链路聚合；访问 / 异常 / API 日志由 Observe 阶段中间件与普通端点过滤器写入；差异日志由 `AopEvents` 产生；链路追踪按 `traceId` 聚合。
- **配置参数**：`Settings` 的参数（平台 + 租户覆盖、加密）、字典（树形项）、业务编号沿用；框架 `Configuration.*` 只用于远程配置 / 密钥（可选 Nacos），不混用。
- **缓存**：`ISharedCache` / `ICache`；Redis 开启时 `Caching.Redis` + `Caching.Hybrid`；`Maintenance` 的缓存管理只对带应用前缀的键开放。

### 5.14 Schema、种子与升级

### 6.3 契约层

- `gen-contracts`：读 `contracts/openapi.json`，用 `openapi-typescript` 生成 `types.ts`；自写发射器按 `operationId`（即操作 ID）生成 `operations.ts`：

  ```ts
  export const users = {
    list: (req: UsersListRequest, o?: CallOptions) => invoke<UsersListRequest, PageResult<UserListItem>>('users.list', req, o),
    get:  (req: { id: string }) => invoke<…>('users.get', req),
    lock: (req: { id: string; reason?: string }) => invoke<…>('users.lock', req),
  }
  ```

  `invoke` 从生成的路由表（方法、模板、参数落点）拼请求；`permissions.ts` 从 OpenAPI 的 `x-xihan-permission` 与 `components.x-xihan-permissions` 导出 `Permission` 字面量联合、`operationPermission` 映射与权限定义（码、显示名、说明，供授权界面生成）；`enums.ts` 导出枚举成员与 `enumLabel(type, value)`（文案从后端 `metadata.enums.list` 按语言取，缓存）。DataAnnotations 折进 Schema 后，生成的类型自带 `minLength` / `maximum` 这类约束，表单可直接复用为前置校验。上传、下载这类普通端点也在同一份文档里（D1），发射器按其 `operationId` 生成 `FormData` 入参 / `Blob` 出参的调用，前端不再手写文件客户端。
- 请求头：`Authorization: Bearer`、`Accept-Language`（当前区域）、`traceparent`（每请求生成，日志关联）、可选 `xihan-deadline`。不再有 `X-Timezone`、`X-Language`、`X-Request-Id`、签名 / 加密头（开放接口是服务端到服务端的事）。成功响应不带 trace id 头：客户端自己生成了 `traceparent`，排障时以它为准；失败响应的 `traceId` 由 Problem Details 携带（2026-10-27 确认不加 `xihan-trace-id`）。
- 错误：`ApiError { code, status, detail, traceId }`；`detail` 已按 `Accept-Language` 本地化，直接展示；分支只看 `code`：`SECURITY_DENIED_001`（未认证）→ 刷新令牌一次后重放，失败登出；`IDENTITY_DENIED_002`（锁屏）→ 锁屏钩子；`KERNEL_UNAVAILABLE_001`（维护中）→ 维护提示。
- 门禁 `check-contracts`：CI 用后端 `contracts export` 重新生成并要求 diff 为空；`check-permissions`：视图里引用的权限码必须存在于生成的 `permissions.ts`（取代 4.x 读后端 `PageRegistry.cs` 源码的正则测试）。

### 6.4 认证、租户与权限门控

- 登录流程、2FA 票据、找回密码、第三方登录回调、切换租户（换令牌后整页重载）、模仿（横幅 + 退出模仿）沿用 4.x 行为，接口换为 `auth.*` / `impersonation.*` 操作。
- `auth.permissions` 一次返回权限码、菜单树、页面码、作用侧；`usePermission().can('identity.users.create')` 精确匹配，不认通配。
- 路由 `meta.permission` 来自页面登记的权限码；按钮 `v-if="can(permission)"`；Schema 页的 `actions[].permission` 直接填操作权限码。

### 6.5 路由与菜单

后端菜单驱动动态路由沿用：`component` 字段是 kebab 路径，前端 `import.meta.glob('/src/modules/*/views/**/*.vue')` 以「去掉模块段」后的键匹配，撞键在 `validate-modules` 门禁报错；`_core/*` 由 `packages/views` 的显式表解析。守卫顺序沿用（白名单 → 用户上下文 → 装载路由 → 权限校验 → 标签页）。路由包与 4.x 相同（修订（十九））：`packages/router` 的 `guard.ts` / `dynamic.ts` / `routes/core.ts` 与应用侧 `src/router`（RootLayout 承载业务页、hash 缺省）原样沿用，只是权限与菜单的数据来源换成 `auth.permissions`，组件按页面登记精确解析。

## 9. 风险与需要回灌框架的事项

### 9.1 N0 冒烟验证项

原来列在这里的五项技术风险（多库事务、实体级落点、Validate 拿类型化请求、OpenAPI 权限码）已由框架补齐（ADR-0022、0024、0031），剩下四项只是冒烟确认。**N0 结论（2026-10-28）：四项全部通过**，用例在 `backend-next/test/XiHan.BasicApp.Integration.Tests/Smoke/`：

| 验证项 | 影响 | 做法 | 结论 |
| --- | --- | --- | --- |

### 9.2 其他风险
