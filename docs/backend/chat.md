# 在线聊天

本页说明在线聊天的会话与消息规则、语音与视频通话、推送、附件、部门群同步、聊天审计、策略参数与保留清理，适用于后端与前端开发者。

Chat 是 Tier 3 的可选模块：单聊、群聊、部门群与 AI 助手会话，消息的发送、撤回、编辑、回应、置顶、转发、已读与提及，语音与视频通话（单聊里一对一，群聊与部门群里多人，可以共享屏幕），聊天 Hub 与聊天审计。

## 数据

六张租户库表（`TenantScoped*`），平台一侧以 `platform` 为租户落在同一张表里，平台账号之间同样能聊天；独立库的租户在自己的库里。

| 表 | 说明 |
| --- | --- |
| `sys_chat_conversation` | 会话：类型（单聊、群聊、部门群、助手）、名称、头像、单聊唯一键、部门、群主、助手、成员数、最大消息序号、最后消息、公告、描述；软删除，不进差异日志 |
| `sys_chat_conversation_member` | 成员：角色（群主、管理员、成员）、未读数、已读到的消息与序号、免打扰、置顶、禁言、入会时间；退群与移出即软删除 |
| `sys_chat_message` | 消息：会话内序号、发送人与名字快照、类型、正文、附件（JSON）、撤回、编辑、回复快照、提及（点名的成员与提及所有人）、置顶；不软删除，按保留期物理删除 |
| `sys_chat_message_reaction` | 表情回应：同一消息、同一用户、同一表情只有一条 |
| `sys_chat_call` | 通话：会话、发起人、媒体（语音、视频）、状态、结束的原因、响铃到几时、接通与结束时间、通话记录消息；不进差异日志 |
| `sys_chat_call_participant` | 通话的参与者：状态（受邀、已加入、已拒绝、未接听、已离开）、加入与离开时间；同一通话里一个用户只有一行 |

会话内的消息按序号排序：发消息时对会话行加一取得序号（行锁让同一会话的发送串行），历史的游标、已读位与已读回执都比序号。主键是 GUIDv7，同一毫秒内没有先后，不能用来排序。

## 规则

| 规则 | 说明 |
| --- | --- |
| 单聊 | 同一对用户每侧只有一个，没有即建；不能和自己单聊 |
| 群聊 | 含群主至少两人，发起人为群主；加人、移出、改信息与公告、禁言要群主或管理员，转让群主与设管理员只有群主；群主不能退群或被移出；没有解散 |
| 部门群 | 只有本部门的成员能进，打开时补齐部门现有成员；没有群主与管理员，所以没人能改信息、置顶消息或禁言；名称随部门、不能改；平台没有部门，部门群只在租户一侧 |
| 成员范围 | 加进会话的人必须属于当前一侧：平台是注册在平台的账号，租户是注册在本租户的用户与租户成员（`CHAT_VALIDATION_021`） |
| 发送 | 只有成员、没被禁言；文本必填不超过 4000 个字符，图片与文件至少一个附件（可带说明），语音恰好一个附件、1 到 60 秒、没有正文；系统提示、助手回复、通话记录与聊天记录只由服务端追加 |
| 提及与回复 | 最多提及 20 名成员；提及所有人（`mentionAll`）只有群聊的群主与管理员能用（`CHAT_DENIED_002`），单聊、助手会话与部门群用不了（`CHAT_VALIDATION_033`，部门群没有群主与管理员）；只能回复本会话未撤回的消息，存「发送人: 内容」快照 |
| 撤回 | 本人、发出 2 分钟内，清空正文、保留行与附件；通话记录不能撤回 |
| 编辑 | 本人的文本、发出 5 分钟内、没被禁言 |
| 置顶消息 | 单聊双方都能，群与部门群只有群主与管理员，每会话最多 10 条（`CHAT_CONFLICT_001`） |
| 转发 | 在服务端做：同一个会话里的一条或多条（最多 50 条，不同会话的不能一起转，`CHAT_VALIDATION_034`）转到一个或多个会话。逐条转发按原来的先后原样复制类型、正文与附件，不带转发来源，助手回复按文本转出；合并转发（`merge`）收成一条聊天记录。系统提示、通话记录与已撤回的不能转发（`CHAT_VALIDATION_022`），不是成员或被禁言的会话逐项失败 |
| 聊天记录 | 合并转发出来的一条类型为 `Record` 的消息：发送人是转发的人，正文是 JSON（`sourceType`、`sourceName`、`participants`、`items`，每条带发送人、原来的时间、类型、正文与附件），附件列是里面所有消息的附件，目标会话的成员凭它换得到下载地址；会话预览写「[聊天记录]」。它能再被转发、再被合并（套在里面），不进会话内搜索；正文超过 50 万个字符即拒绝（`CHAT_VALIDATION_035`） |
| 已读 | 未读清零、已读位前移（不回退，没给消息即读到最新），已读位推给全体成员 |

系统提示（建群、邀请、退群、移出、转让）与会话预览按发起调用的区域写进库里，公告以操作人的身份进消息流。

前端在消息的右键菜单里进多选：勾选能转发的消息（系统提示、通话记录与已撤回的选不了），输入区换成操作条，逐条或合并转发到选中的会话；聊天记录在消息流里是一张卡片（标题、前几行、条数），点开按原来的先后列出里面的消息，套着的聊天记录能再点进去。群主与管理员在群聊的提及列表里多一项「所有人」，收到的人会话列表里出「有人@我」、气泡高亮。

## 助手会话

一个用户对一个助手只有一个会话，打开时没有即建并发开场白。助手不是成员，不算未读，助手会话也不显示已读回执。回复是前端发出用户消息之后单独发起的调用：

1. 前端发出提问，再调 `chat-messages.reply-assistant`，带自己生成的 `replyId`。
2. 服务端从库里取最近的提问与回复，经 Contracts 的 `IChatAssistants` 流式生成。Chat 不引用 AI，AI 关掉时没有实现，三个助手操作（`chat-conversations.assistants`、`open-assistant`、`chat-messages.reply-assistant`）返回 503 `CHAT_UNAVAILABLE_001`，聊天其余功能照常。
3. 生成期间这次调用还没开事务，增量经立即推送发给本人（`ChatAssistantDelta`）。
4. 结束后过敏感词（与用户输入同一套），落库为一条助手消息（超过 20000 个字符截断），提交之后按普通消息推送，再推 `ChatAssistantCompleted`。

失败（模型不可达、空输出、敏感词、提示词停用、检索失败）时不留消息，操作以 Problem Details 结束，同时立即推 `ChatAssistantCompleted` 带 `errorCode` 与 `error`。

| 错误码 | 说明 |
| --- | --- |
| `CHAT_VALIDATION_026` | 不是助手会话 |
| `CHAT_VALIDATION_027` | 会话里没有可回答的提问 |
| `CHAT_UNAVAILABLE_001` | 助手不可用（AI 没有装配） |
| `CHAT_UNAVAILABLE_002` | 生成失败。原因只有异常类型，完整异常看应用日志 |
| `CHAT_UNAVAILABLE_003` | 模型没有产生任何内容 |

助手本身的配置见 [AI 能力](./ai#助手)。

## 语音与视频通话

单聊里是一对一通话，群聊与部门群里是多人通话，通话中可以共享屏幕。媒体在浏览器之间走 WebRTC：多人通话里每两个人之间各一条连接（全互联，不经媒体服务器），能直连就直连，直连不通时经 TURN 中继；服务端只记通话的状态、转发信令，不经手也不录制媒体。

### 状态

| 通话的状态 | 说明 |
| --- | --- |
| `Ringing` | 响铃中：发起人已加入，还没有别人进来 |
| `Ongoing` | 通话中：有人接听或加入过 |
| `Ended` | 已结束，带结束的原因 |

| 参与者的状态 | 说明 |
| --- | --- |
| `Invited` | 受邀，在响铃 |
| `Joined` | 在通话里 |
| `Rejected` | 拒绝了 |
| `Missed` | 没接到：响铃到点、响铃时离线，或发起时占线、不在线没能响铃 |
| `Left` | 离开了 |

| 结束的原因 | 说明 |
| --- | --- |
| `Completed` | 通话中的人陆续挂断，剩下不到两个人 |
| `Cancelled` | 没人接之前发起人挂断，或发起人离线 |
| `Rejected` | 受邀的人都拒绝了（响铃时受邀的人挂断也算拒绝） |
| `Missed` | 受邀的人都没来，其中有人没接到（响铃到点、离线，或没能响铃） |
| `Interrupted` | 通话中有人离线，剩下不到两个人 |

### 规则

| 规则 | 说明 |
| --- | --- |
| 发起 | 单聊呼叫对方：自己与对方都不在别的通话里（受邀还没接也算占着），对方此刻在线，否则不响铃、直接拒绝。群聊与部门群点名邀请成员（`inviteeUserIds`）：不能为空、都得是会话成员、连发起人在内不超过人数上限；占线与不在线的受邀人不响铃、记成没接到，一个能响铃的都没有即拒绝；一个会话同一时刻只有一通。助手会话不能通话 |
| 人数上限 | 读 `chat.policy`：语音 `callMaxVoiceParticipants`（缺省 8），视频 `callMaxVideoParticipants`（缺省 6）。发起时按受邀的人数核对，接听与加入时按已经在通话里的人数核对 |
| 接听与拒绝 | 只有受邀还没答复的人、通话还没结束时；多端同时接听只有先到的成功，其余端随推送停铃。有人接听即接通，别的受邀人照常响铃 |
| 加入 | 多人通话还没结束时会话成员都能加入（`chat-calls.join`）：没被邀请的、拒绝过的、没接到的、离开了的都能来；人数满了即拒绝 |
| 挂断 | 没人接时发起人挂断即取消，受邀的人在响铃时挂断即拒绝；通话中挂断即离开，剩下不到两个人、又没人还在响铃时通话结束；已经结束的、早就不在里面的照样成功（几个人可能同时挂） |
| 响铃到点 | 响铃秒数读 `chat.policy` 的 `callRingSeconds`（缺省 60）。到点由端上来挂：发起端准点挂，受邀端晚 2 秒挂掉自己那份邀请；服务端把到点前 3 秒起的挂断一律记未接听 |
| 离线 | 用户离线（过了[离线宽限](#在线状态)）即离开他占着的通话：受邀的记没接到，没人接时发起人离线即取消，通话中的记离开、剩下的人不够时以中断结束 |
| 收尾 | 内建作业 `chat.calls.sweep` 每 5 分钟按平台与每个租户收一遍没人管的通话（响铃过点、发起人已离线、通话中已经离线的人与过点还挂着的邀请）；停用的租户跳过 |
| 先后 | 同一会话里的发起、接听、拒绝、加入、挂断对会话行加锁排成先后：两个人同时互相呼叫只成一通，一个群里不会同时起两通。锁只在会话上，两个不同会话里的人在同一瞬间呼叫同一个人时可能各响一通，先接的成立，另一通到点记未接听 |

### 通话记录

通话结束时往会话里追加一条类型为 `Call` 的消息：发送人是发起人，正文是 JSON（`callId`、`media`、`reason`、`durationSeconds`、`missedUserIds`），会话预览写「[语音通话]」或「[视频通话]」。只给没接到的人（`missedUserIds`）各记一条未读，接通过的、自己拒绝的与没被邀请的不记。通话记录不能撤回、不能转发，也不进会话内搜索；聊天审计里显示为「媒体 · 结果」。

### 信令与穿透

- 信令经聊天 Hub：占着通话的端调 `CallSignal(callId, toUserId, data)`，服务端核对它是这通接通了的电话里的人，把 `ChatCallSignal`（`callId`、`fromUserId`、`data`）转出去：给了 `toUserId` 只转给他（他也得在通话里），没给转给已经加入的其他人。`data` 是两端之间约定的 JSON，不超过 20000 个字符，服务端不解析、不落库：会话描述与 ICE 候选指给一个人，麦克风、摄像头与屏幕共享的开关发给所有人。
- 通话每次变化推 `ChatCallChanged`，载荷是通话此刻的样子，发给参与过这通电话的每个人的全部连接；多人通话另发给正开着这个会话的连接（会话组），没被邀请的成员据此看到有通话在进行。打开会话时用 `chat-calls.ongoing` 取这个会话里还没结束的那一通。
- 穿透服务器由 `chat-calls.ice-servers` 给出，取自宿主配置 `BasicApp:Chat:Calls`（见[配置](../configuration#basicapp-chat-calls)）。TURN 用共享密钥的限时凭据：用户名是「到期秒数:用户」，凭据是它的 HMAC-SHA1，按调用方现签，密钥不下发。都不配也能用，只是只有同一网段或能直连的两端打得通。

### 媒体连接与屏幕共享

- 通话里每两个人之间一条连接，后加入通话的一方出 offer（同一毫秒加入的比用户 ID），两端各自按同一份参与者算，不会同时出。有人离开只关与他的那条，他再加入时重新建。
- 每条连接在协商时按固定次序留好三个轨道位：麦克风、摄像头、屏幕。之后开关摄像头、换设备、开始与停止共享屏幕都只是往位上换轨道，不重新协商；对端凭位置认出是哪一路。
- 屏幕共享在语音与视频通话里都有：浏览器让用户挑整个屏幕、一个窗口或一个标签页，只共享画面、不带系统声音；从浏览器自己的「停止共享」上停掉也算停止。不支持的浏览器（多数手机浏览器）不出这个按钮。
- 全互联里每个人要给其余每个人各发一路媒体，上行带宽随人数增长，人数上限按此定；人更多要换成经媒体服务器转发的架构。

### 前端

- 会话头有语音与视频按钮：单聊直接呼叫对方；群聊与部门群先开点名的对话框，列出会话成员，不在线的选不了，最多选到人数上限减一。通话记录的气泡可点，用同样的媒体再打一次。
- 群里有通话在进行时，会话顶上出一条横幅（谁发起的、几个人在里面），没在里面的成员点「加入」即进通话；自己已经在别处接听的只显示提示。
- 来电卡片与通话窗挂在布局根部：任何页面都能接听，离开聊天页通话不断。多人通话的来电写明是哪个群。通话窗可拖动、收拢成标题栏或铺满视口，里面一人一格（还在响铃的也占一格，连不上的标出来），有人共享屏幕时屏幕占主画面、各人收成底下一排；有静音、关摄像头、共享屏幕、换麦克风与摄像头（浏览器支持时还有扬声器）与挂断。
- 来电在每个开着的页签都响；只有发起、接听或加入的那个页签建媒体连接、处理信令，别的页签随推送停铃。没有 `chat.chat-calls.call` 的人不出来电卡片，那份邀请到点记没接到。
- 与一个人之间 30 秒媒体还没连上、或连接断开 8 秒没恢复，这条连接作废、他那一格标成连不上；与所有人都这样了，端上自己挂断并提示。
- 响应与推送之间没有先后：接听、加入的请求在路上时到过推送的，以推送为准，不拿可能更旧的响应对齐连接。
- 刷新页面：还在等自己答复的来电经 `chat-calls.active` 认回来；刷新之前占着通话的那个页签，媒体已经随页面没了，回来后替自己挂断（多人通话里别人照常，可以从横幅再加入）。
- 浏览器只在 HTTPS 与 `localhost` 下给麦克风、摄像头与屏幕。

| `chat.chat-conversations.manage` | 建群与群治理（进操作日志） |
| `chat.chat-audit.read` | 聊天审计 |
| `chat.chat-calls.read` | 查看自己此刻所在的通话与所在会话里的通话，取通话设置与穿透服务器 |
| `chat.chat-calls.call` | 发起、接听、拒绝、加入与挂断通话（进操作日志） |

权限码两侧都有。套餐白名单与角色的授权是运营数据，种子只在首次写入：已有的套餐与角色不会自动带上之后新增的权限码，要在套餐页与角色页授予。页面 `chat.conversations`（`/chat/conversations`）与 `chat.audit`（`/chat/audit`）在「消息中心」目录下。

## 选人

`chat-conversations.user-options` 供发起单聊、建群与加成员：列出当前一侧的正常账号（范围同上面的「成员范围」），只要会话读权限，不要身份的用户读权限与组织的归属读权限。

| 参数 | 说明 |
| --- | --- |
| `keyword` | 匹配用户名与显示名 |
| `departmentId` | 只看这个部门及其全部下级里任职的人；平台没有部门 |
| `skip`、`limit` | 按显示名排序逐页取，`limit` 缺省 50、最大 500 |

响应的 `hasMore` 说明后面还有没有；每个人带头像文件与主部门的名称（没有任职或在平台一侧为空）。会话成员（`members`）同样带头像文件。

前端的选人是可勾选的候选列表：可搜索、可只看最近联系人（取自单聊会话）或按部门筛选，往下逐页加载；多选时旁边列出已选的人，换一批候选也留着。加成员时已在群里的人照样列出、标注而不可选。会话的资料、公告、个人设置（置顶、免打扰）与成员治理都在会话详情里：宽屏是消息流旁边的第三栏，放不下时顶替消息流。

## 推送

聊天 Hub `/hubs/chat` 由 Chat 登记、宿主一并映射，认证、会话门禁与连接登记同通知 Hub（见[实时推送](./realtime)）。推送按成员点发给会话这一侧的用户，在调用提交之后发出；配了 Redis 时跨实例。

| 方向 | 方法 |
| --- | --- |
| 服务端推送 | `ReceiveChatMessage`、`ChatMessageRecalled`、`ChatConversationChanged`（11 种变更）、`ChatTyping`、`ChatMessageEdited`、`ChatReactionChanged`、`ChatReadPositionChanged`、`ChatPresenceChanged`、`ChatAssistantDelta`、`ChatAssistantCompleted`、`ChatCallChanged`、`ChatCallSignal` |
| 客户端可调 | `JoinConversation`（核对成员后加入会话组）、`LeaveConversation`、`Typing`（核对成员后组播给组里的其他连接，不落库）、`CallSignal`（核对是接通了的通话里的人后转给指定的人或通话里的其他人，不落库） |

`ChatConversationChanged` 的变更种类：`created`、`member-added`、`member-removed`、`info-changed`、`owner-transferred`、`member-silenced`、`member-role-changed`、`pinned-changed`、`member-setting-changed`、`department-joined`、`department-kicked`。

## 在线状态

在线即此刻在这一侧持有实时连接（任一 Hub 都算，见[实时推送](./realtime#在线状态)）。

- 读的时候带当时的状态：会话列表的单聊带 `peerOnline`，会话成员与选人候选带 `isOnline`。
- 之后的变化推 `ChatPresenceChanged`（`userId`、`isOnline`）：Chat 订阅 Realtime 的 `basicapp.realtime.presence-changed`，按处理时的在线状态推，乱序或重复投递推出去的都是当时的事实。
- 受众是他的单聊对端（按人点发），以及正开着他所在的群或部门群的连接（会话组，即调过 `JoinConversation` 的连接）；不按群的全体成员扇出，没参加任何会话的人不推。
- 刷新页面、断线重连不闪：最后一条连接断开后有一段宽限（缺省 8 秒），宽限内又连上即不推离线，只在回来时补推一次在线。

前端把读回来的状态与推来的变化记在同一处，头像右下角的绿点、单聊头部与详情里的「在线 / 离线」、群成员的在线人数都从那里取；实时连接连上时（断线重连，或会话列表在连接建好之前就读了）把会话列表与当前会话的成员重取一遍。

## 附件

附件以会话为访问范围，经 Files 的附件契约 `IAttachmentFiles` 存取：上传与秒传只要聊天的发送权限，文件存在调用方这一侧、来源记 `chat`，大小上限与存储配额同普通上传；发送时核对附件是自己在聊天里上传的（`CHAT_DENIED_009`），文件名与大小以文件记录为准；会话成员经 `chat-messages.presign` 凭会话换签名地址，附件须出现在这个会话的消息里，或是自己上传、还没发出的文件。文件管理照旧要 `files.files.read`。保留清理不删附件文件。

群头像是文件主键或直链：给文件主键时同样须是自己在聊天里上传的（`CHAT_DENIED_009`），设上之后会话成员经 `chat-messages.presign` 凭会话换它的地址。单聊的头像是对端用户的头像。

## 部门群同步

Organization 在加入与移出部门时记领域事件 `basicapp.organization.membership-changed`（随写入进发件箱），Chat 订阅它：已经建了的部门群里，进了部门即入群、移出部门即出群，并推会话变更（被移出的人也收到）。处理时按当时的归属核对，消息乱序或重复投递都只做一次；写库失败即投递失败、由消息代理重试。

## 聊天审计

持 `chat.chat-audit.read` 即看当前一侧全部会话的消息，不要求是成员：

- 列表按关键字（正文、发送人名、附件）与会话、发送人、消息类型（含通话记录与聊天记录）、发送时间、是否撤回筛选，缺省不含已撤回的，筛选 `includeRecalled` 为 `true` 即都看；
- 消息详情带所在会话、附件、提及（含提及所有人）、回复与表情回应；
- 会话成员列出会话与它现在的成员。

撤回清空的正文与编辑前的正文不另留。

## 策略与保留清理

参数 `chat.policy`（JSON，种子建好的内建参数，租户可建同键参数覆盖敏感词、响铃秒数与通话人数上限），缺省值：

```json
{ "retentionDays": 365, "sensitiveWords": [], "callRingSeconds": 60, "callMaxVoiceParticipants": 8, "callMaxVideoParticipants": 6 }
```

| 字段 | 说明 |
| --- | --- |
| `retentionDays` | 消息保留天数，1 到 3650，只读平台的值 |
| `sensitiveWords` | 敏感词，不区分大小写的包含匹配；租户建了同键参数即用租户的；管发送与编辑的正文（含图片与文件的说明），不管群名、公告与文件名（`CHAT_VALIDATION_023`） |
| `callRingSeconds` | 通话响铃秒数，10 到 300；到点没人接即未接听；租户建了同键参数即用租户的 |
| `callMaxVoiceParticipants` | 语音通话连发起人在内的人数上限，2 到 12；租户建了同键参数即用租户的 |
| `callMaxVideoParticipants` | 视频通话连发起人在内的人数上限，2 到 8；租户建了同键参数即用租户的 |

JSON 不合法、保留天数、响铃秒数或人数上限越界即 `CHAT_VALIDATION_024`，发送、通话与清理都不按错误的值执行。前端经 `chat-calls.settings` 取响铃秒数与两个人数上限。

内建作业 `chat.messages.cleanup` 每天 04:00（UTC）按平台与每个租户逐个清理（独立库的租户清它自己的库）：先删所属消息已过期的表情回应，再删过期的消息；不删会话、成员与附件文件。一侧失败只记日志，不影响其他侧。

## 开关

`BasicApp:Modules:Chat:Enabled`（缺省开）。关掉后宿主不装配 Chat：权限目录、页面、Hub、附件上传端点、两个内建作业与部门归属、在线状态的订阅都不在，菜单不下发、操作 404；Organization 照常发出领域事件，没有订阅方。六张表仍由正式库的基线脚本建出（开发库的 `InitTables` 只建装配了的包的表）。
