数据库配置 ​

本页说明数据库连接、从库与 SQL 日志、多库落点、数据访问方式与建表策略，适用于后端开发者与部署人员。

数据层是 SqlSugar（框架 Persistence.SqlSugar 的「方式一」：应用提供连接配置回调）。支持 PostgreSQL（缺省）、MySQL 与 SQL Server（Oracle 在做），表结构由 ORM 按实体建出（见建表策略）；CI 在每种库上跑全量集成测试，日常的集成测试用 SQLite 跑。不引入 EF Core 作为平行的业务数据层。

支持的数据库 ​

库provider要求说明
PostgreSQLpostgresql14 及以上缺省库
MySQLmysql8.0.13 及以上，字符集 utf8mb4软删除实体的唯一索引是函数索引，8.0.13 起才有
SQL Serversqlserver实测 2022，库要打开 READ_COMMITTED_SNAPSHOT字符串列建成 nvarchar；缺省的读已提交是加锁读，读未提交的行要等写入方结束，在调用事务之外另开连接的读会一直等到超时。还没有表的新库由结构升级打开；已有表的库没打开即升级失败，由 DBA 执行 ALTER DATABASE [库名] SET READ_COMMITTED_SNAPSHOT ON
Oracleoracle还不能部署能建表，但 Oracle 把空字符串当 NULL，框架与 BasicApp 按空字符串存取的值还没有改完；库是 DBA 事先建好的用户（CreateDatabase 不建），字符串列建成 nvarchar2，最长 2000 个字符
SQLitesqlite—只给测试用

各库的差异由 ORM 与框架约定抹平，实体照常写：

  • 字符串列的长度按字符计。SQL Server 与 Oracle 建成 Unicode 类型（nvarchar / nvarchar2）；超过 2000 个字符的列写 [LongText]（Oracle 的 nvarchar2 装不下），长文本列不能进索引。
  • 索引键不超过 MySQL 的 3072 字节（utf8mb4 每字符 4 字节）与 SQL Server 的 1700 字节（每字符 2 字节）：单列字符串索引最长 768 个字符，组合索引按各列之和算。集成测试 ColumnWidthTests 逐个核对全部实体。
  • 日期时间列精度到微秒（MySQL datetime(6)、Oracle timestamp(6)）。
  • 软删除实体的唯一索引只约束未删除的行：PostgreSQL、SQL Server 是带条件的索引，MySQL 与 Oracle 是函数索引；可空列为空的行不参与唯一，各库一致。
  • 关键字搜索（Contains / StartsWith / EndsWith）按字面匹配，大小写照各库自己的规则：PostgreSQL 与 Oracle 区分大小写，MySQL 与 SQL Server 按库的排序规则（缺省不区分），SQLite 只对 ASCII 字母不区分。

平台库连接 ​

连接写在框架的服务绑定 XiHan:Bindings:db：

json
{
  "XiHan": {
    "Bindings": {
      "db": {
        "type": "connection:relational",
        "value": "Host=<主机>;Port=5432;Database=<库名>;Username=<用户>;Password=<密码>",
        "provider": "postgresql"
      }
    }
  }
}
  • 数据库是启动硬要求：绑定缺失或为空即 RUNTIME_VALIDATION_001 中断启动，不回退到任何内存实现。
  • provider 不写即 postgresql（也认 postgres / pgsql / npgsql），另认 mysql、sqlserver（mssql）、oracle、sqlite；写了别的即 RUNTIME_VALIDATION_002。
  • 不提交真实连接串：appsettings.json 不写绑定，本机开发写在 appsettings.Development.json，部署用环境变量 XiHan__Bindings__db__value 或 Kubernetes Service Binding。
  • 语句超时 XiHan:Persistence:SqlSugar:CommandTimeoutSeconds（缺省 300 秒）。

从库与 SQL 日志 ​

BasicApp:Database 只管平台库：

键缺省说明
Replicas不配平台库的从库列表，每项 ConnectionString 必填、HitRate 是读权重。配了之后只读工作单元读从库，会写的工作单元读写都走主库
LogSqlfalse记录每条 SQL（只记语句，不记参数值），只在排查时打开
LogSqlErrorstrue记录执行出错的 SQL
LogSlowSqltrue记录慢 SQL
SlowSqlThresholdMilliseconds1000慢 SQL 阈值

从库只给平台库，独立库租户读写都走它自己的库。从库的缺省权重、健康探测、摘除与恢复在 XiHan:Persistence:SqlSugar:Replicas。决定授权的读取（会话门禁、角色指派、权限规则、访问策略等）经 StoreScope.ReadPrimaryAsync 钉在主库，不读落后的从库。SQL 日志的类别是 XiHan.BasicApp.Sql。

方式一回调：SqlSugarRuntime ​

宿主以 new SqlSugarPersistenceFeature(SqlSugarRuntime.ConfigureWith(configuration)) { DiffLog = DiffLogBuffer.IsLogged } 装配持久化。回调对默认连接调用一次，带分片的调用再对 shard 连接调用一次：

项内容
库类型与连接串读绑定 db（分片连接由框架按租户目录推出）
命名约定只给框架的数据库记录：表名、列名 snake_case（AuditRecord → audit_record）；BasicApp 的实体显式写 [SugarTable] / [SugarColumn]，不经这条约定
操作人AopEvents.DataExecuting 填 CreatedBy / ModifiedBy / DeletedBy
字符串缺省长度框架记录里没有 [LongText] / [StringLength] / [MaxLength] 的字符串列一律 varchar(512)；BasicApp 的实体在 [SugarColumn] 里写长度
建表只增不改已有的表不删列、不改列：SqlSugar 缺省会删掉实体里没有的列、按实体改已有列的类型、长度与可空，正式库上会丢数据或改写大表
差异日志全审计实体的写入带差异事件，供数据变更日志使用；标了 [DiffLogIgnored] 的实体除外
从库与 SQL 日志按 BasicApp:Database 挂上

框架随后施加协议约定：主键、并发戳（长度 32）、软删除、租户列、DateTimeOffset 按 UTC 往返、日期时间列精度、SQL Server 与 Oracle 的 Unicode 字符串列、可空列。

多库：默认连接与租户分片 ​

作用域客户端带两个连接：default（平台库）与 shard（带分片的租户调用才有）。框架按顺序决定实体落点：

  1. 实体带 [Tenant(configId)] 的，落指定的连接；
  2. 实现 IMultiTenant 且调用有 shard 连接的，落分片连接；
  3. 其余落默认连接。

共库（字段隔离）的租户调用没有 shard 连接，租户库实体与平台库同库、靠 tenant_id 过滤。独立库租户的连接串存在租户目录（TenantRecord 的 ConnectionString / DatabaseProvider 属性），以 ISecretProtector 密文保存；框架按租户目录建分片连接，Runtime 的 ProtectedTenantShardResolver 解密，解不开即 RUNTIME_UNAVAILABLE_004，不降级为共库。

跨库事务不是两阶段提交

工作单元在第一次写入时开事务，之后首次取用的连接再补开；提交与回滚逐连接进行，是顺序提交：第二个连接提交失败时第一个已经提交。需要严格原子的写入放在同一个库里。租户开通只写平台库（租户与框架租户目录同一个工作单元）；独立库的建库建表是单独的操作 tenants.initialize-database，结果写回租户，失败可改连接后重试。

数据访问 ​

场景用什么约束
按 ID 取、按规约列、计数、增删改、批量IRepository<TEntity, Guid>（Feature 里 AddGeneratedRepositories() 登记）自动处理租户、软删除、并发戳、时间；EntityQuery 的 Take 只收 1–1000
分页、投影、联表、聚合包内 Queries/，用 ISqlSugarClient必须以 TenantScopedQuery.For<T>(context) 或 For<T>(client, context) 起手（按落点取连接，补软删除与租户条件）；平台库里分侧的实体再接 OwnedByCurrentTenantOrPlatform(context) 或 OwnedByCurrentTenant(context)
平台一侧的租户库实体Runtime 的 SideRows框架仓储要求调用带租户；平台一侧的行（platform）经它按侧读写，写之前开事务
按月分表的日志仓储按 [SplitTable(SplitType.Month)] 自动走分表入口，EntityQuery<T>.Within(from, to) 限定扫描的表；Queries/ 里用 .SplitTable(from, to)不给时间范围即扫全部分表
独立于调用事务的读写Runtime.Persistence.StoreScope.ReadAsync / ReadPrimaryAsync / WriteAsync失败计数、会话门禁、读穿缓存的加载
后台对租户库的工作框架 TenantShardScope 或 Contracts 的 ITenantScopeRunner在自建作用域里按租户绑定分片

框架没有全局查询过滤器：直接用 ISqlSugarClient 而不经 TenantScopedQuery 起手，就会漏掉租户与软删除条件。直接用客户端写入（Insertable 等）之前要先调 SqlSugarUnitOfWork.EnsureTransactionAsync，写入才在本次调用的事务里。

只读操作（动词 get / list 或声明 ReadOnly = true）跑在只读工作单元里，写入即 500 PERSISTENCE_UNEXPECTED_001；要补建的行放到写操作里建，读路径缺行按缺省值读。

建表策略 ​

环境方式
开发XiHan:Persistence:SqlSugar:InitTables 为 true（appsettings.Development.json 已打开）：启动时按已登记的实体建缺表、加缺列，再补建部分唯一索引
正式表结构升级器在启动时执行：新库按实体建全部表；已有库先执行比台账新的升级脚本，再按实体补缺的表与列，见表结构升级

两条路径都只建缺表、加缺列，不删、不改已有的列。给已有行的表新增非可空列时：数值、枚举、布尔、Guid 列在 PostgreSQL 上按 CLR 缺省值回填；非可空的字符串与日期时间列不受支持，应在实体里声明成可空，或写升级脚本先加列并回填。

测试库 ​

用例库
绝大多数集成测试SQLite 临时库，经 BasicAppTestServer 走完整管道
PostgreSQL 用例（两库冒烟、从库读主库、并发发号、Provider 一致性、表结构升级等）读环境变量 XIHAN_TEST_POSTGRES（服务器级连接串，不含库名），测试自建临时库；没设置即跳过
整套换一种库跑环境变量 XIHAN_TEST_DB 设为 postgresql、mysql、sqlserver 或 oracle，每个用例在 XIHAN_TEST_POSTGRES、XIHAN_TEST_MYSQL、XIHAN_TEST_SQLSERVER、XIHAN_TEST_ORACLE 指向的服务器上建临时库（Oracle 是临时用户，连接账号要能建用户）；选了库却没配服务器即失败。直接用 SQLite 语句准备数据的用例固定在 SQLite 上

CI（.github/workflows/ci.yml）的主作业起 postgres:17-alpine 服务并设置 XIHAN_TEST_POSTGRES；另有一组作业按库各跑一遍集成测试（PostgreSQL 17、MySQL 8.4、SQL Server 2022），测试库关掉刷盘以缩短建表时间。
